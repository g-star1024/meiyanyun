## 1. 两卡方案要点

### 1.1 卡A 后端：三写端点 + 校验/审计/DataScope + 富化读（commit `c257165`）

改造前 `org_unit` 只有 `GET /api/org/tree` 只读能力，组织结构调整只能手工改库；且 tree 返回字段贫瘠（无负责人/编制/停用原因），前端详情区只能靠 mock 补齐。本卡补齐写闭环：

- **新增 `OrgAdminController`（+309 行）**：三个写端点全部 `@RequirePerm("org:manage")`，中文 400/404 拒绝，每动作一条合法 JSON 审计。
- **三写端点语义**：
  - **新建 `POST /api/org/admin/org-units`**：仅允许在**门店下新建部门**（parentCode 必须指向 `org_type='门店'` 的节点，否则中文 400）；`orgCode` 服务端强制 `toUpperCase()` 归一后落库并做唯一性校验；`orgType` 服务端固定写「部门」，不接收前端传值；`region`/`storeCode` 由父门店继承推导，不由前端指定。
  - **编辑 `PUT /api/org/admin/org-units/{orgCode}`**：**缺省=保持、空串=清空、非空=更新** 的三态语义；`orgCode`/`orgType` 不可改（请求体带了也忽略）；`parentCode` **仅部门可下发**（跨门店移动同时联动改写 `store_code`/`region`），门店/大区/集团节点传 parentCode 一律中文 400。
  - **启停 `POST /api/org/admin/org-units/{orgCode}/toggle-status`**：body `{enable:boolean, reason?:string}`；**停用必须带 reason**（trim 后非空，否则中文 400），落 `inactive_reason`；**启用时强制清空 `inactive_reason`**（避免历史停用原因残留误导）；状态与目标一致时**幂等成功且不重复写审计**。
- **DataScope 隔离**：三写端点统一走 `assertManageable(orgCode)` —— 越权目标**不返回 403 而是中文 404**「数据不存在或无权查看」，避免通过状态码差异探测他区组织编码是否存在（枚举探测防护）。REGION_MGR 仅可管辖本大区节点，STORE_MGR 仅可管辖本门店子树。
- **富化读（`OrgController` +15 行）**：`GET /api/org/tree` 节点补 `leaderName`/`headcount`/`remark`/`inactiveReason`，让前端详情区可全量接真。**注意：`/tree` 只挂 `@RequirePerm("org:view")` 且不做 DataScope** —— 组织目录属全局可见信息（跨店转诊/审批路由都要读全树），隔离交由写端点 `assertManageable` 兜底，此为**既有设计**，本卡未改动。
- **实体扩列（`OrgUnit.java` +25/-2）**：新增 `leaderName`/`headcount`/`remark`/`inactiveReason` 四列，业务表走 ddl-auto=update 自动加列，**不写 Flyway**（铁律）。

### 1.2 卡B 前端：T1OrgView 去 mock + 写边界收窄（commit `079d4b9`）

- **`api/org.ts`（+61）**：新增 `createOrgUnit`/`updateOrgUnit`/`toggleOrgUnitStatus` 三个写接口与 `OrgUnitCreatePayload`/`OrgUnitUpdatePayload`/`ToggleStatusPayload` 契约类型；`OrgUnit` 补齐四个富化字段，可空字段显式 `| null`（vue-tsc 严格模式下 `undefined` 与 `null` 不可混用）。
- **`stores/m1Org.ts`（重写 205 行）**：删除全部 mock 数据源，改为 `GET /org/tree` 拉取后 `flatten` 成扁平表；三个命令改 async 且成功后 `await load(true)` 强制回源刷新（不做乐观更新，避免服务端归一化结果——如编码大写、跨店移动后的 region 继承——与前端本地状态不一致）；`update` 中仅当 `cur.type === 'DEPT'` 且 parentId 确实变化时才下发 `parentCode`；停用缺原因在前端即抛「停用组织单元必须填写原因」。
- **`views/T1OrgView.vue`（+213/-189，样式 0 行变更）**：
  - 树头按钮文案由「新建组织」收窄为 **「新建部门」**；新建抽屉标题同步；
  - 新建抽屉字段序：名称* / 编码* / 类型（**disabled 固定"部门"**）/ 上级门店* / 负责人 / 编制人数 / 排序 / 备注，**无状态字段**（状态只能走启停弹窗）；
  - **上级下拉只列门店**（过滤 org_type='门店'），集团/大区/部门不出现在候选中；未选上级点创建 → 前端校验「请选择上级门店」且抽屉不关闭；
  - 编辑抽屉：**编码 textbox disabled、类型不可选**，上级门店可改（跨店移动入口），仍无状态字段；
  - 停用弹窗「停用组织单元」含「停用原因 *」multiline，**「确认停用」按钮初始 disabled**（原因非空才解锁，前端硬约束）；启用弹窗「启用组织单元」**无原因字段**；
  - 后端中文 `message` 直出 toast；提交期禁用按钮防重复提交。

## 2. 后端设计

### 2.1 表结构（无新表，ddl-auto=update 自动演进）

`org_unit` 真实 DDL（容器内 `\d org_unit` 实证）：

| 列 | 类型 | 说明 |
|---|---|---|
| org_code | varchar(16) PK | 组织编码，**服务端强制大写归一** |
| org_name | varchar(64) | 名称 |
| **org_type** | varchar(8) CHECK ∈ (集团\|区域\|门店\|部门) | **列名是 org_type 不是 org_type_code**（后者是 API 层字段名）；中文枚举带 CHECK 约束 |
| parent_code | varchar(16) FK→org_unit | 上级节点，自引用外键 |
| store_code | varchar(16) FK→store | 归属门店，部门跨店移动时联动改写 |
| region | varchar(8) | 大区，由父门店继承推导 |
| sort_no | int not null default 0 | 排序 |
| created_at | timestamptz | 创建时间 |
| **status** | varchar(8) | 启用/停用，**列名是 status 不是 status_code** |
| leader_name | varchar(32) | B33 新增，负责人 |
| headcount | int | B33 新增，编制人数 |
| remark | varchar(255) | B33 新增，备注 |
| inactive_reason | varchar(255) | B33 新增，停用原因（启用时强制清空） |

> 排查提示：SQL 查询请使用真实列名 `org_type`/`status`；用 API 字段名 `org_type_code`/`status_code` 查库会报 `column does not exist`。

### 2.2 端点清单（4 个，复用既有 org-service 网关路由，网关零改动）

| 方法 | 路径 | 权限 | 说明 | 批次 |
|---|---|---|---|---|
| GET | /api/org/tree | org:view | 返回**裸根对象**（无 data 包装）；本卡补 4 个富化字段；**不做 DataScope** | 既有，卡A 富化 |
| POST | /api/org/admin/org-units | org:manage | 仅门店下建部门；编码大写归一+唯一校验；审计 CREATE | 卡A 新增 |
| PUT | /api/org/admin/org-units/{orgCode} | org:manage | 三态语义；编码/类型不可改；仅部门可移动；审计 UPDATE | 卡A 新增 |
| POST | /api/org/admin/org-units/{orgCode}/toggle-status | org:manage | 停用必填 reason，启用清 reason，同态幂等不重复审计；审计 DISABLE/ENABLE | 卡A 新增 |

### 2.3 审计动作（biz_type=ORG，payload 合法 JSON）

| action | 触发 | 关键字段 |
|---|---|---|
| CREATE | 新建部门 | orgCode（大写后）、orgName、parentCode、storeCode、region |
| UPDATE | 编辑/跨店移动 | orgCode、变更字段集；跨店时含 `toStore` |
| DISABLE | 停用 | orgCode、reason |
| ENABLE | 启用 | orgCode（无 reason 字段） |

同态幂等调用不产生审计行（取证中 ENABLE 对已启用节点重复调用，audit 计数未增）。

## 4. 已知缺口 / Backlog

- **组织树写能力仅覆盖「部门」层级**：门店/大区/集团节点的新建与移动仍需手工改库。这是有意收窄——门店主数据有独立的 `store` 域与开店流程，大区/集团调整属低频重大变更，不宜开放自助 UI。列 Backlog。
- **`GET /api/org/tree` 不做 DataScope**：组织目录全局可见为既有设计（审批路由/跨店转诊依赖读全树），隔离由写端点 `assertManageable` 兜底。若后续要求目录也隔离，需同步评估审批与转诊链路影响。
- **兼岗上级路由**（SLA 自动升级、审批 REGION 阶段指派）仍依赖组织树兼岗模型完善，本批未涉及，继续留在「组织树收口批」Backlog。
- 部门删除（物理删）未开放，只提供停用；如需回收编码需人工介入。
