## 一、目标与边界

### 1.1 目标

1. **赠金 gift_balance 全链路**：充值可录入赠送金额（giftAmount，分）；卡台账落 gift_amount/gift_after 双列；消费/划扣先赠金后本金（giftUsed=min(赠金余额, 本次金额)）；**赠金只动卡台账，不进 finance 资金分录**（fund_entry 无赠金行，赠金不是商户实收资金）；售卡赠金恒为 0（售卡链路 giftBalance 固定 0L 不变）。
2. **退卡中冻结**：发起退卡即冻卡——member_card 在用→退卡中、写 ADJUST 台账（amount=0、biz_ref=CC 单号-**F**、operator=system）；冻结期充值/消费/划扣全部中文校验拦截（「卡状态非『在用』（当前：退卡中），不可充值/划扣」）；**驳回→解冻**（退卡中→在用，ADJUST biz_ref=CC 单号-**U**，本金/赠金原额不变）；**终审通过→refundCard 置「已退卡」**，本金/赠金清零、走退款资金分录（无 -U，终局态不解冻）。
3. **划扣双签金额分级**：reviewer 必须是 org 域真实在职员工工号——txn 经 X-Internal-Token 调 org `GET /api/org/internal/staff/{id}` 硬校验（工号不存在 400、已离职 400、org 服务不可用 **502 硬失败不降级**，划扣不执行）；禁止操作人同人自签；分级闸门：**L1（<¥5,000）** 复核人须为 DOCTOR/OPERATOR/FRONT_DESK/STORE_MGR 四角色之一互签，**L2（¥5,000~20,000）/L3（≥¥20,000）** 复核人须为 STORE_MGR 店长，L3 额外附「区域经理知晓/报备」提示文案；审计留痕「双签划扣完成（tier 级），复核人：工号 姓名」+ 审计 jsonb 落 tier/amount。
4. **前端配套**：卡务页充值面板加赠送金额字段与口径提示、卡资产区分本金/赠送、流水橙色 +赠展示、冻结态隐藏充值/去划扣按钮且储值总额不计冻结卡；划扣台复核人改真实工号选择（带姓名回显）与分级徽章；退卡发起按钮 cardcancel:create 门控。页面视觉与交互样式零改动。
5. **双栈真实验证**：seed 栈 API E2E + PG 数据域对账 + 浏览器截图全链路；prod 栈同物部署 + 网关只读冒烟（不制造业务残留）。

### 1.2 边界红线（拍板落实）

| 决策点 | 结论 | 落实方式 |
|---|---|---|
| **赠金资金口径** | 只动卡台账 | gift_amount/gift_after 落 card_ledger；finance fund_entry **无赠金分录**（充值只按实收本金发 RF-DEPOSIT/IN）；赠金消费时本金部分照常结转收入，赠金部分不产生资金流 |
| **售卡赠金** | 恒为 0 | 售卡开卡 giftBalance 固定 0L；赠金仅来自门店充值录入 |
| **冻结台账类型** | 复用 ADJUST | 冻结/解冻写 ADJUST、amount=0、biz_ref=CC 单号-F/-U、operator=system，不动 Flyway CHECK 约束；与真实资金变动（RECHARGE/CONSUME/REFUND）天然区分 |
| **冻结期操作** | 一律硬拦截 | recharge/consume/writeoff/refundForOrder 入口校验卡状态非「在用」即 400 中文，不依赖前端隐藏按钮（后端兜底） |
| **驳回复位** | 原额解冻 | 解冻不重算余额，卡余额/赠金以冻结前为准（冻结期间本就无任何资金变动），-U 台账与 -F 对称留痕 |
| **复核人校验** | 真实工号硬校验 | org internal staff profile 端点为唯一数据源；org 不可用 502（**不降级放行**，宁可划扣失败不可假双签）；404/离职 400 中文 |
| **分级阈值** | 后端常量唯一来源 | TxnService.L2_MIN=500,000 分（¥5,000）、L3_MIN=2,000,000 分（¥20,000），tierFor() 统一计算；前端只做相对文案（L1 基础签署/L2 双签/L3 三签·高审），不硬编码金额 |
| **同人双签** | 禁止 | operator 与 reviewer 工号相同 → 400 中文 |
| **金额口径** | bigint 存分 | 后端全程分（long），前端元↔分换算；充值 DTO 字段 amount/giftAmount（分） |
| **内部端点鉴权** | X-Internal-Token | org `/internal/staff/{id}` 挂 internal:name-map、customer freeze/unfreeze 挂 internal:card-write，仅系统身份放行，普通登录人 403 |

## 五、问题与教训

### 5.1 缺陷：L1 分级错误文案金额与阈值常量不一致（<¥1,000 vs <¥5,000）

- **现象**：交付文档核查时发现 OrgStaffClient.requireReviewerRole 的 L1 拦截文案写「本笔划扣为 L1 级（<¥1,000）」，但真实分级阈值 TxnService.L2_MIN=500,000 分（¥5,000）——L1 应为 **<¥5,000**；同文件 L2「¥5,000~20,000」、L3「≥¥20,000」文案均正确。
- **根因**：文案手写金额时沿用了早期讨论稿的 1,000 阈值，未与最终落地的 tierFor 常量同源核对；前端 tier 文案均为相对描述（L1 基础签署/L2 双签/L3 三签·高审）无硬编码金额，故 bug 仅后端一处。
- **修复**：文案改「L1 级（<¥5,000）」，mvn 重建 txn-service fat jar，seed+prod 双栈重新部署（jar md5 `1774a4353848` 双栈一致）；反编译 class 常量池核验「L1 级（<¥5,000）」在、旧「1,000」0 次出现。
- **教训**：**错误提示里的金额/阈值必须引用分级常量口径逐一核对**，分级规则改阈值时要全局搜文案中的金额数字；阈值常量唯一来源在后端 tierFor()，前端与提示文案都不得另写金额。

### 5.2 缺陷：CInput 二次封装未透传 input 事件——复核人工号实时检索失效

- **现象**：划扣台复核人工号框输入时无候选下拉。根因是公共组件 CInput.vue 只 emit `update:modelValue`（v-model），未 emit 原生 `input`，而划扣台按既有页面惯例监听 @input 做实时检索。
- **修复**：CInput onInput 同时 emit update:modelValue 与 input；顺带给 CSelect 补 disabled prop 与置灰样式（冻结态下拉需要）。
- **教训**：**二次封装组件必须透传原生事件**（input/change/blur），否则调用方按原生 DOM 约定写的监听会静默失效——这类问题不报错、只表现为「功能没反应」，须靠真实页面操作才能发现。

### 5.3 环境与工具备忘

1. **prod 账号体系与 seed 不同**：SE/SST 门店工号仅 seed 存在，prod 冒烟用 E0xx 通用工号（E014 SUPER_ADMIN）；登录 401 时先换工号再怀疑密码。
2. **充值 DTO 字段名**：RechargeReq record 字段为 `amount/giftAmount/payMethod`（单位：分），不是 amountFen/giftFen——curl 报「充值金额必须为正」先核对字段名。
3. **PG 列名**：card_ledger 是 `change_type/operator`（非 type/operator_id），赠金列 `gift_amount/gift_after`；writeoff_desk_task 单号列是 `wd_no`（非 task_no）、timeline 是 varchar 需 ::text 强转再读 jsonb；txn_card_cancel 手续费列是 `fee`（非 fee_amt）。
4. **curl**：`--noproxy '*' -sk -H "Authorization: Bearer $TOKEN"`，URL 必须 https://localhost:18443（seed）/8443（prod）。
5. **冻结/解冻台账识别**：ADJUST amount=0、biz_ref 后缀 -F（freeze）/-U（unfreeze）、operator=system；终审退卡只有 -F 无 -U（终局态），驳回才有对称 -U。

## 六、双栈回归结论

- **seed**：赠金/冻结/双签三条链路全绿——充值赠金落台账双列且 fund_entry 无赠金分录（售卡赠金恒 0）；退卡发起即冻卡（在用→退卡中 + ADJUST -F）、冻结期充值 400 中文拦截、驳回对称解冻（-U，余额原额）、终审清零退款（已退卡 + RF-REFUND/RF-DEPOSIT 成对）；L1 划扣真实工号双签（SE001→SE003 江医生，timeline 工号+姓名+tier 留痕），不存在工号/离职/同人/L2L3 非店长/org 不可用五类闸门全部 400/502 正确拦截；浏览器冻结态/解冻态/赠金展示截图齐验，console 零报错。
- **prod**：三服务 + 前端与 seed 同物（bundle index-UPIfyIV1.js、jar 三指纹一致）、新列自动建齐、E014 登录 + 7 GET 端点全 200（含 /api/txn/card-cancel）、无业务残留。
- 既有功能回归：B16 售卡/开卡/预收链路（OD 售卡单 RF-DEPOSIT 预收口径未动）、B17 审批中心/退款单主链路、收银台收款等既有域在本轮部署验证中正常，未受赠金/冻结/双签改动影响。

## 七、本批明确不做（移交后续）

1. **L3 第三签系统流**：本批 L3 为「店长双签 + 区域经理报备文案提示」，未建区域经理账号的系统内第三签审批节点（报备仅提示留痕，无独立审批流）。
2. **赠金高级规则**：赠金有效期/过期清零、满赠活动自动赠送（本批为手工录入）、赠金消费的营销侧报表统计口径。
3. **退卡手续费财务联动**：fee 已落单（fee_rate/fee_manual_override），但手续费收入科目的 fund_entry 分录联动留后续。
4. **冻结时效管理**：退卡审批超时提醒/自动解冻/冻结期 SLA 监控。
5. **双签复核人前端候选过滤**：本批候选按工号/姓名检索全量在职员工，未按「本店 + 持相应角色」在前端预过滤（后端闸门已硬校验，不影响安全）。
