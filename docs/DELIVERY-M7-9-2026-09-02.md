## 一、本批解决的问题（DoD 验收中实证发现并修复的 4 个真实缺陷）

### 1. 种子员工两套工号口径漂移，新环境开箱缺人（m7-9b 修复）

M4 时代联调员工 E001-E014 仅存在于手工 `db/seed_org.sql`（psql 灌 core 库），**不在启动播种器内**——新环境/重置后 core 库无 E 系列，dev-login 选人、越权用例全部失去基线；而 seed 库另有 SE001-SE024（SST0x 门店世界）。源码真源与运行库长期漂移（M7 首批报告即登记的风险项）。

- **固化**：E001-E014 十四人固化为 `RbacDataInitializer.CORE_SEED_STAFF` 启动幂等播种（含医疗执照标记 E003/E008/E010、E011 华东大区），与 EXTRA_STAFF（SE101-SE105）、SE001-SE024（SQL 灌 seed 库）三套工号体系统一到「启动幂等 + 种子 SQL」两个真源。
- **外键安全**：`staff.store_code` 有外键 `staff_store_code_fkey` 指向门店主数据。CORE_SEED_STAFF 的门店是 ST-SH-001/ST-SH-002/ST-BJ-001（core 世界），seed 库门店为 SST01-SST06——直接跨库播种触发外键违例，`@Transactional run()` 整体回滚（实测 seed 库连 SE101-105 都未播上）。修复：播种前从 `orgUnitRepo.findAll()` 构本库门店集合，门店不在本库的行 `store_code` 置 NULL（集团员工口径），不挂本库门店业务。
- **终态**：core staff = 19 行（E14 + SE10x5，E005=ST-SH-001、E011=华东）；seed staff = 43 行（E14 门店全 NULL + SE00x24 + SE10x5）；两库 0 重复工号，重复启动幂等不增行。

### 2. dev-login 门店级角色选人回归（m7-9b 修复）

seed 库补播 E 系列后，`role=STORE_MGR` 登录返回 E005（store=None）——字典序 E<SE，门店级角色被「毒化」到无门店归属的集团口径员工上，登录后无本店数据上下文。

- 修复 [AuthController.devLogin](../backend/org-service/src/main/java/com/meiyun/org/AuthController.java)：STORE 域角色优先选 `storeCode` 非空的第一人，无则回退第一人；集团角色（GROUP/REGION 域）不受影响。
- 终验四角色：seed STORE_MGR=SE001/SST01、seed SUPER_ADMIN=E014、core STORE_MGR=E005/ST-SH-001、core REGION_MGR=E011/华东。

### 3. Bean Validation 英文默认消息外露（DoD-2 真实缺陷，m7-9a 修复）

txn 预约空体提交返回 `["project: must not be blank","apptDate: must not be null"...]`——`@NotBlank/@NotNull` 默认消息英文直出，违反「中文错误零英文外露」铁律。

- 根因：meiyun-common 是纯 Java 零依赖模块不能放 web advice；各服务自有 GlobalExceptionHandler 未覆盖校验异常。
- 修复：新建公共模块 [ChineseValidationAdvice.java](../backend/meiyun-security/src/main/java/com/meiyun/security/ChineseValidationAdvice.java)（`@RestControllerAdvice`，`MethodArgumentNotValidException` → 422，body `{timestamp,status,message:"参数校验未通过："+字段+中文}`，注解 code 映射：NotBlank/NotEmpty→不能为空、NotNull→不能缺省、Size→长度不符合要求、Min/Max→数值超出允许范围、Pattern→格式不正确等），注册到 `MeiyunSecurityAutoConfiguration`，**所有依赖 meiyun-security 的服务自动生效**；删除 txn 服务返回英文的旧 422 处理器。

### 4. 兜底 ExceptionHandler 抢先吞异常成 500 英文堆栈（DoD-2/6 连带缺陷，m7-9a 修复）

customer-service 商城商品空体提交返回 HTTP 500 `{"code":"INTERNAL","message":"Validation failed for argument [0]...must not be blank..."}`——同一 `@RestControllerAdvice` 内 `@ExceptionHandler(Exception.class)` 兜底方法抢先拦截了校验异常，公共 advice 的专用 422 处理器不生效；且兜底消息 `ex.getMessage()` 把英文堆栈/内部信息直接外露（org 服务兜底还含英文 "internal error"）。

- 修复：customer、org 两个 GlobalExceptionHandler 各显式声明 `MethodArgumentNotValidException` 422 中文处理器（专用 handler 优先于兜底）；兜底 500 消息统一改为「系统繁忙，请稍后重试」，原始异常只进容器日志不外露。
- 全站扫：txn/customer/org 三服务异常处理器 + 公共 advice 全部核查，无其他英文外露点。

## 五、M7 里程碑总结

**目标回顾**：后端零鉴权（0 个 @PreAuthorize）是 M7 开工时最大安全敞口。经 m7-1~m7-9 九个批次：

- **立法**：RBAC 数据模型（role_permission / permission_def，8 角色对齐前端矩阵，剔除 STORE_MANAGER）+ 权限矩阵 35 资源 7 动作；
- **执法**：meiyun-security 公共模块统一拦截器 + 注解，全站写接口鉴权覆盖；纵向越权（低角色调高权限接口 403）、横向越权（他店数据 404 不泄露存在性）curl 用例全过；
- **数据权限**：data_scope 四级（本店/本区域/集团等）查询注入，店长只见本店、区域见辖区、集团见全部；
- **登录态**：JWT 无状态（HMAC-SHA256，claims sub/name/roles/store/scope/perms），dev-login 联调入口；
- **审计可信**：哈希链 SHA256（微秒精度截断对齐 PG）、actor 全链路收敛 JWT（约 30 处 body 伪造点封堵）、手机号按 `customer:phone:decrypt` 脱敏；
- **中文铁律**：401/403/404/422/400/500 全异常路径中文零外露；
- **种子真源**：三套工号体系统一，新环境开箱幂等。

**M7 后端范围 100% 交付并真实验证**。遗留前端项（RBAC 管理页/审计日志查询页去 mock）随 M5 前端批次推进，不阻塞里程碑闭环。
