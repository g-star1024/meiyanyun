## 一、目标与边界

### 1.1 目标

1. **三条卡核销路径 seed 栈真跑 + 资金/台账对账**：
   - 路径① **划扣台双签扣次**：/writeoff-desk 到店建单（WalkinCmd）→ 双签执行（ExecuteCmd，执行人 ≠ 复核人）→ customer writeoff() 扣次数/扣余额 → WO 单号 → emitWriteoffDone 成对结转；
   - 路径② **收银台储值余额支付扣尽**：服务单 /order 创建 → /confirm 双签 → /pay（method=balance + cardNo）→ txn PaymentService 调 customer consume() 扣余额 → 收齐已收款；
   - 路径③ **直连卡扣次**：POST /txn/writeoff（WriteoffCmd，sign1/sign2 双签）→ customer writeoff() 扣次 → WO 单号 → 成对结转。
2. **修复售卡单误入整单核销**：后端 order-writeoff 对 bizKind=CARD_SALE 返回 400 中文；OrderView 全端点补 bizKind 出参；前端整单核销页过滤 CARD_SALE（前后端双拦）。
3. **储值卡扣尽置「已用完」**：CardLedgerService.consume() 余额扣尽（after==0 且储值卡，或疗程卡余额与次数双尽）时状态流转「在用 → 已用完」，审计 json 记 depleted。
4. **前端动线「去划扣」**：CardCourseView 卡资产区（储值卡/疗程卡两处）在用卡加「去划扣」按钮 → 跳 /m2-writeoff-desk 并 query 带出客户/卡 → 自动打开「直接到店建单」弹层预填客户与卡（项目现场填写），复用划扣台双签，不绕开合规。样式零改动。
5. **双栈真实验证**：seed 栈三路径真跑 + 数据对账 + 浏览器动线截图；prod 栈同物部署 + 只读冒烟（不制造业务残留）。

## 五、问题与教训

### 5.1 缺陷：储值卡余额扣尽不置「已用完」（状态机漏洞）

- **现象**：储值卡（card_type=CARD）经收银台余额支付把余额花光后，member_card.status 仍是「在用」——卡列表/卡页永远展示一张余额 0 的「在用」卡，客户到店划扣时才在余额不足处报错。
- **根因**：卡状态流转只写在 CardLedgerService.writeoff()（扣次路径，判 remainTimes==0）；而储值卡走 consume()（余额支付路径），旧实现只 `setBalance(after)` 不看状态。且储值卡 total_times/remain_times 是占位值（issue 时 total=remain，B16 售出的 CD-002 模板甚至 total_times=10），**不能用 remainTimes 判储值卡扣尽**。
- **修复**：consume() 以 card_type 权威判定——`after==0 && ("CARD".equals(cardType) || remainTimes==null||0)` → 已用完；疗程卡须余额与次数双尽才置（余额 0 仍有余次时保留纯扣次 0 额划扣能力）。审计 json 落 depleted 便于追溯。
- **教训**：**同一业务状态（卡用完）有两条写路径时，状态流转规则必须两条路径都覆盖**，且判定字段要选该卡型的权威口径（储值卡看余额、疗程卡看次数），不能拿一种卡型的占位字段去判另一种卡型。

### 5.2 缺陷：售卡单误入整单核销（履约模型错位）

- **现象**：B16 售卡单（bizKind=CARD_SALE）收款后是「已收款」状态，会出现在 /writeoff 整单核销待办里；若操作员点整单核销，订单被置「已核销」，但客户手里的会员卡仍「在用」、预收负债仍挂账——收入确认与卡履约完全脱节。
- **根因**：整单核销（order-writeoff）是为**服务零售单**设计的（一次服务一次履约确认）；售卡单的履约是**会员卡随客户到店逐次划扣**（每次划扣走 emitWriteoffDone 结转一笔收入），两种履约模型不同，B16 加 bizKind 时未在核销入口设卡。
- **修复**：前后端双拦——后端 order-writeoff 幂等查重前先判 CARD_SALE → 400 中文指引（请在划扣台/卡扣次核销）；前端待核销列表 filter bizKind!=='CARD_SALE'（正常流程看不见，直接调 API 也被 400 兜住）。
- **教训**：**新订单类型（bizKind）落地时，必须过一遍所有「按状态捞单」的既有入口**（核销、退款、报表、交接班…），逐一判断该类型是否适用；只在创建处打标、不在消费处设卡，等于没打。

### 5.3 环境与工具备忘

1. **deploy.sh 无 `svc` 聚合参数**：合法 component 为 `frontend|backend|all|<svc>-service|gateway`；部署单个服务用 `deploy.sh seed txn-service --skip-build`（handoff 曾误记 `svc`）。
2. **docker exec 不支持 heredoc**：`docker exec meiyun-pg psql ... <<'EOF'` 无输出，多条 SQL 用多个 `-c "..."` 参数。
3. **列名先 `\d 表名`**：card_ledger 主键是 `ledger_id`（非 id）、writeoff_record 是 `writeoff_id`、writeoff_desk_task 操作人列是 `operator/reviewer`（非 actor）、order_payment 主键是 `payment_id`；finance_event 无 ref_no 列，按 biz_ref 查 fund_entry。
4. **prod 网关登录响应无 data 包装**：8443 /api/org/auth/login 直接返回 `{token,...}`（seed 18443 同），脚本取 token 用 `json.load(...)["token"]`。
