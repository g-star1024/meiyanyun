## 〇、设计总原则

1. **B/C 隔离红线**：C 端用户＝顾客（customer），B 端用户＝员工（staff）——token 体系、签名密钥、鉴权链路、权限模型完全独立，**绝不复用 staff JWT/RBAC**；C 端身份＝微信 openid 绑定的会员，一切数据按 customer_id 行级隔离，绝不越权读他人。
2. **绝不假装已连通（DESIGN-P5-B57 §0.5／DESIGN-T3 红线②承接）**：manifest appid 占位 `REPLACE_WITH_YOUR_WEAPP_APPID`、无商户支付凭证——code2session/prepay 外呼失败是预期常态，如实返回错误码＋中文 message，**禁止伪造登录态/伪造支付成功/随机造数据**；dev-login 照 B 端 dev-login 先例**默认关闭**（显式配置开关，仅 seed 联调栈开启）。
3. **数据同源**：C 端视图＝B 端既有业务数据的顾客侧投影（预约/订单/卡券/积分共用单库 meiyun_core），不建第二套业务库——「独立会员体系」（PLAN 口径）仅指 C 端账号绑定层（openid↔customer）独立。C 端写操作（预约/下单）落 B 端既有业务表，走目标域 internal 端点（X-Internal-Token，照 T3 org→txn 先例）保事务与审计。
4. **三处一致（铁律 1）**：前端 API_BASE→网关 TLS :8443→第 10 条路由 `/api/c`→c-service:8090（SEED 18090），逐段落地；网关零鉴权改动——`/api/c` 照 `/api/public` 先例透传，C 端 token 由 c-service 自验（独立 JWT 密钥配置）。
5. **前端签名/结构保留**：mp-uniapp 22 页 pages.json/tabBar/组件结构零改动；6 个 seed store（member/pricelist/appointment/order/coupon/followup）导出签名全保留切真（铁律-1-B 照 B 端惯例）；8 个页面写死数据改由 store/接口驱动；request.ts 既有约定保留（Bearer mp_token＋X-Tenant-Id＋{code,message,data} 包约 code 0/200 成功＋401 clearToken）。

| 列 | 型 | 约束 |
|---|---|---|
| id | BIGSERIAL | PK |
