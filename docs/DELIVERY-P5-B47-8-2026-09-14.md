## 1. 背景与目标

A1 AI 中心第 8 张切真卡，也是 P5-B47 批次与本轮夜间自主队列的**最后一张卡**。原 A1PrivacyView 为纯 mock 页（假 KPI：48 脱敏字段 / 96% 达标 / 2 待处理 / 12840 审计；假规则 M1–M8、假等保项 C1–C8、假导出历史），本卡将其三 tab 整页接到真实持久化与统一审计链：

1. **敏感字段脱敏规则**（tab 1）：8 条固定规则码（PM-SEED-01~08），覆盖手机号/证件/姓名/金额/银行卡/地址/诊疗记录/邮箱八类字段，标注所在模块与脱敏类型，区域经理可启停、店长只读。
2. **等保合规自评**（tab 2）：8 项检查项（PC-SEED-01~08，对应等保 2.0 物理/网络/主机/应用/数据/管理等条线），达标勾选可双向翻转。
3. **审计导出**（tab 3）：按北京时区日期区间导出统一审计日志，导出文件以 **SHA-256 全链哈希**（canonical 头 + 区间内 audit_log 的 id/prev_hash/cur_hash/payload 规范化拼接）封存，导出历史可查、可校验；区间校验、跨度上限、空区间口径均有诚实处理。

隐私合规页是**管理/治理面而非 AI invoke 功能**：不接 FeatureCatalog、不走模型绑定/灰度/配额计费、无 AI 出站调用；三类写动作（启停脱敏、翻转达标、生成导出）经 AI_PRIVACY 审计 biz_type 留痕，审计幂等动作码与哈希导出报告可互相溯源。

**诚实边界**（不伪造闭环）：全站个人数据查阅/删除请求工单流、授权同意（consent）生命周期管理、等保口径定期巡检任务等跨服务合规流程不在本卡范围，登记 §8 Backlog；本卡只实现页面已承诺的脱敏规则治理、合规自评与审计哈希导出三件事。

### 2.4 PrivacyService（265 行，5 个 record 契约）

- **stats 四 KPI（口径诚实，全部真算）**：
  - `maskFieldCount` = 脱敏规则总数 = 8（规则码为固定治理目录，非仅启用数）；
  - `compliancePct` = `Math.round(checked*100.0/total)`，清场态 7/8 = **88**；
  - `pendingCount` = 停用规则数 + 未达标项数 = 1+1 = **2**；
  - `auditCount` = **audit_log 中 biz_type=AI_PRIVACY 的计数 + ai_privacy_export 流水计数**（页面「审计」KPI 即本治理动作产生的审计总量，导出本身也产审计，随生成联动增长）。
- **toggle 两方法刻意不加方法级事务**：仓储 save 自行提交后在新持久化上下文回读，确保 PG 触发器刷新的 updated_at 与经办值回读到前端（B47 卡5/卡7 同款前置规避）；仅在状态真翻转时落审计，同态重放幂等零审计（本卡验证均为真翻转，549/550 为清场复位翻转）。
- **createExport（L154–197，本卡核心）**：
  - 区间按**北京时区（UTC+8）**解释：`from` 当日 00:00 ≤ audit_log.created_at < `to` 次日 00:00；跨度上限 `RANGE_SPAN_MAX_DAYS=366`；倒置/超跨度/缺日期均中文 400；
  - 区间内按 id 升序拉取 id/prev_hash/cur_hash/payload；
  - **canonical 报文**：首行 `HEADER|AI_PRIVACY|{from}|{to}|{行数}\n`，其后每行 `{id}|{prev_hash}|{cur_hash}|{normalizePayload(payload)}\n`；normalize 用 Jackson readTree→writeValueAsString 做 JSON 规范化（解析异常回退原文、null 归一为空串），消除字段顺序/空白差异；
  - `report_hash` = 整段 canonical 的 SHA-256 Hex（64 位小写）；**空区间也生成报告**（只有头行，auditCount=0），与非空导出走同一套哈希可校验流程；
  - 落 ai_privacy_export 一行并追加 EXPORT_REPORT 审计（payload 含 rangeFrom/rangeTo/auditCount/reportHash）。
- 审计动作码 txn_no：`PM-RULE-{id}` / `PC-ITEM-{id}` / `PM-EXPORT-{exportId}`。

## 5. 真验过程发现与修复

1. **audit_log 列名排错**：初查审计误用不存在的 `subject_id` 列报错 `column "subject_id" does not exist`，经 information_schema 核对实际九列（id/biz_type/txn_no/actor/action/payload/prev_hash/cur_hash/created_at），经办人工号在 **actor** 列，改查 action/actor/payload 后全部证据落位。
2. **手工 JWT 注入失败改账密登录**：内联拷贝的长 JWT 少 2 字符（5466 vs 5468）致签名损坏，首个请求 401 被 client 拦截器 clearAuth 登出；放弃注入，改为在登录页走真实 POST /api/org/auth/login（E005/meiyun123，dev-login 已关闭），只读降级三 tab 由此在真实鉴权链路下验证（JWT claim 名为 `perms`、登录响应字段为 `permissions`）。
3. **auditCount KPI 口径拍板**：页面「审计条数」最初只查 audit_log，导出动作产生的 EXPORT_REPORT 会让页面数字与导出历史割裂；最终口径定为 audit_log AI_PRIVACY 计数 + export 流水计数，并在 547/548 两次导出后实测联动，口径写入本文件 §2.4。
4. **截图 filePath 限制**：Chrome DevTools MCP 截图 filePoint 受 workspace roots 限制无法落仓库路径，改为内联返回 + DOM/console 断言取证，不影响验证结论。
5. **fat-jar 陈旧预防**：沿用 B47 卡5/卡7 纪律直接 `mvn package`（非 compile）重打 fat-jar 再重建，V29 一次 applied 成功，未复现 B38 陈旧 jar 不迁移问题。
