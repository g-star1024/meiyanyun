## 一、目标与边界

### 1.1 目标

1. **床位房间档案持久化**：房间（治疗室/咨询室/观察室/恢复室等类型）与床位（编号、所属房间）建档落库；床位维护停用态（OK/MAINTENANCE + 维护原因）真实持久化，设维护/维护恢复写操作日志 + 全审计。
2. **设备仪器台账持久化**：设备建档（资产编号/名称/分类/品牌型号/位置/购置金额/使用年限/下次校准·维保日期）、状态机（正常 NORMAL / 校准中 CALIBRATING / 维修中 REPAIRING / 停用 DISABLED）、校准/维保/维修记录登记；记录回写规则由服务端统一执行——登记 CALIBRATION 记录且设备处于 CALIBRATING 时自动复位 NORMAL、费用累加累计折旧、下次日期回写设备主档。
3. **前端接真实 API、样式零改动**：/m2-rooms、/m2-equipment 两页由纯演示态切换为真实 API 读写（api 层 + Pinia store 接线），失败回落 demo 数据；页面既有视觉与交互零改动。
4. **种子与脚本**：store-service 启动播种 9 房 16 床 / 8 设备 11 条校准维保记录（meiyun_seed 门控）；setup-seed-db.sh 追加 5 张业务表 DDL / TRUNCATE / sanity 计数。
5. **双栈真实验证**：seed 栈 curl 读写 E2E + 审计落库核查 + 浏览器真实点击写链路；prod 栈部署 + 网关冒烟 + 鉴权 401/403 实证。

### 1.2 边界红线（设计决策 D1~D4 落实）

| 红线 | 落实方式 |
|---|---|
| **D1 床位实时占用态一期不持久化** | FREE/IN_USE/SANITIZING（空闲/使用中/消毒中）仅前端演示态，刷新复位；**仅主数据**（房间/床位档案 + 维护停用态 maint_status OK/MAINTENANCE）落库。页面入住/退房/消毒交互保留前端演示；床位「设维护/维护恢复」真实持久化（维护恢复后 DB 回 OK，消毒态为前端演示） |
| **D2 设备台账与 finance fin_asset 一期不打通** | 设备运营台账（equipment/equipment_maintenance）独立落 store-service；不写 finance 的 fin_asset，折旧仅在设备台账内以「累计折旧」字段呈现（账面净值 = 购置金额 − 累计折旧），不产生财务分录 |
| 写接口四件套 | 入参校验（房间编号/名称/类型必填、床位数量 1~20、设备资产编号/名称必填、金额非负等，400 中文提示）；幂等（资产编号/房间编号同店唯一约束，重复建档 409 中文）；全审计（ROOM/EQUIPMENT 两类 bizType，JSON payload 含 storeCode/业务主键/变更前后值）；中文错误 |
| 权限 | 查看 `room:view` / `equipment:view`；写操作 `room:edit` / `equipment:edit`；@RequirePerm 注解 + 门店角色数据域强制本店。FINANCE 角色不含这四个权限（SE104 实证三端点全 403） |
| 金额 | 后端 Long「分」（purchase_amount_fen / depreciated_fen / cost_fen），前端「元」展示、提交时元→分换算；读接口出参 purchaseAmount/depreciated/cost（元），写接口入参 purchaseAmountFen/costFen（分） |
| 业务表 JPA ddl-auto | 5 张业务表由 JPA 自动建 + 种子 DataInitializer 播种，不进 Flyway；setup-seed-db.sh 仅维护 DDL 兜底/TRUNCATE/sanity |
| 种子不碰生产库 | StoreMasterDataInitializer 以 spring.datasource.url contains("meiyun_seed") 门控，prod 库零演示播种（prod 由首次部署时空库启动播种验证，正式环境门控生效后不播） |
| 审计链路 | 复用库存域 ConsumableAuditRecorder（RestTemplate POST audit-service /api/audit，X-Internal-Token 内網令牌，失败仅 log.error 不阻断业务）；audit-service 落各栈自己库的 audit_log（biz_type varchar(16)，哈希链） |

## 五、问题与教训

### 5.1 缺陷：新建设备「下次校准/维保日期」漏传（UI 联调拦截）

- **现象**：UI 新建设备弹窗填了下次校准日期 2027-03-07，创建成功但设备详情「下次校准」显示「未设置」；DB equipment.next_calibration_at 为空。
- **根因**：`stores/equipment.ts` 的 addEquipment() 组装 createEquipment 请求时，只传了 storeCode/assetNo/name/brand/model/category/location/status/purchasedAt/purchaseAmountFen/lifespanYears/note，**漏传 nextCalibrationAt/nextMaintenanceAt**；而后端 CreateEquipmentCmd（EquipmentController L121-124）与 EquipmentService（L108-109 parseDate 落库）本就支持这两个字段，api 层 CreateEquipmentCmd 类型也已声明——纯前端 store 组装遗漏。
- **修复**：addEquipment 请求体补两行 `nextCalibrationAt: data.nextCalibrationAt ? new Date(...).toISOString() : undefined`、`nextMaintenanceAt: 同理`；pnpm build 0 error，双栈 frontend 重部署（bundle index-DdO8ecRW.js）。
- **教训**：写接口字段三处一致（后端 Cmd / api 类型 / store 组装）不能只看类型声明，store 组装处是最容易漏字段的一环；UI 联调以「填了什么→DB 落了什么」三对口为验收标准。

### 5.2 环境与工具备忘

1. shell 代理拦截 localhost：curl 必须 `--noproxy '*'`，网关 `-sk`。
2. seed 栈 store/audit/org 等容器带 compose 项目哈希前缀（如 `89ca5f847bd2_meiyun-seed-audit-service`），按名操作容器用后缀匹配。
3. store-service 响应无 Result 包装壳（裸数组/裸 Map）；设备金额读字段为 purchaseAmount/depreciated/cost（元），不要猜 purchaseAmountYuan。
4. Chrome DevTools MCP：uid 每次界面交互后重排，点击前必须重新 take_snapshot；原生 `<input type=date>` 的 spinbutton 不可直接 fill，用 evaluate_script 设 value + 派发 input/change 事件触发 Vue v-model；window.confirm 用 handle_dialog(action=accept)；ask() 二次确认是页面内弹窗（非原生 dialog），需快照定位「确认」按钮。
5. take_screenshot 的 filePath 必须在配置的 workspace roots 内，否则 Access denied；不传 filePath 则内嵌返回图片。
