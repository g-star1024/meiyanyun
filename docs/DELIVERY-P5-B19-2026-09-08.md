## 一、目标与边界

### 1.1 目标

1. **L3 三签审批流**：L3 大额（≥¥20,000）退款 RF / 退卡 CC 审批单由两阶段扩为三阶段——**REVIEW 店长初审 → REGION 区域经理复审 → FINANCE 财务终审**。状态机：
   - L3 REVIEW 店长初审通过：**不回写业务单**（业务单保持 PENDING_REVIEW），审批单 stage→REGION；
   - L3 REGION 区域经理复审通过：回写业务单 PENDING_REVIEW→PENDING_FINANCE（reviewed_by=区域经理）+ **第三签留痕 sign3/signed_at3**，审批单 stage→FINANCE；
   - FINANCE 财务终审通过：confirmRefund 办结（业务单→REFUNDED，finance_by=财务）；
   - 任一阶段可驳回（原因必填），驳回即回写业务单 REJECTED；L2 两阶段、L1 直达财务的旧链路不变。
2. **阶段角色闸门**：REVIEW 须 STORE_MGR、REGION 须 REGION_MGR、FINANCE 须 FINANCE（SUPER_ADMIN 全放行）；越权操作 403 中文提示（「当前阶段需区域经理审批」等）。
3. **候选过滤（闭合 B18 移交 #5）**：`GET /api/org/staff` 支持 storeCode/roleCode/region 三参数——roleCode 匹配主角色 **+ staff_role 兼岗并集**；数据域强制注入（STORE 本店 / REGION 本区门店+大区编制账号 / GROUP 全量），REGION 域 region 参数强制回收到登录人大区禁止跨区取人；划扣台 L1 复核人候选按四角色（DOCTOR/OPERATOR/FRONT_DESK/STORE_MGR）并行拉取并集、排除操作人本人，失败降级本店全量+客户端角色过滤并提示「后端复核人校验仍为权威闸门」。
4. **阈值双轨对齐**：meiyun-common SignTier 与审批中心 TxnService.tierFor 统一为 **L1 <¥5,000 / L2 ¥5,000~19,999 / L3 ≥¥20,000**（500,000/2,000,000 分），DualSignEngineTest 同步更新。
5. **前端配套**：审批中心 stage 类型扩 REVIEW/REGION/FINANCE，阶段 pill/按钮/流转记录/无权提示三阶段贯通；REGION_MGR 角色补 refund:approve/cardcancel:approve 权限（前后端权限矩阵同步）。页面视觉与交互样式零改动。
6. **双栈真实验证**：seed 栈 API E2E + PG 三签列对账 + 浏览器三阶段 UI/划扣候选全链路截图；prod 栈同物部署 + E014 网关只读冒烟（不制造业务残留）。

### 1.2 边界红线（拍板落实）

| 决策点 | 结论 | 落实方式 |
|---|---|---|

## 五、问题与教训

### 5.1 签署列语义辨析：reviewed_by=区域经理而非店长、sign1/sign2 为空

- **现象**：L3 单终审后 PG 对账，初看疑似 bug——reviewed_by=E011（区域经理）而非初审店长 SE001，sign1/sign2 为空。
- **核查结论**：读 TxnService/ApprovalService 代码确认均为设计预期——①L3 REVIEW 店长初审通过**不回写业务单**（保持 PENDING_REVIEW），REGION 复审通过才调 txn.approve 做 PENDING_REVIEW→PENDING_FINANCE 回写，故 reviewed_by 记录的是回写人=区域经理；②sign1/sign2 是收款收银/划扣场景「客户+经办」双签列，与审批链路无关。审批三签留痕 = reviewed_by + sign3/signed_at3（B19 新增）+ finance_by，完整正确。
- **教训**：**审批阶段与业务单回写时机解耦时，「谁回写谁留痕」列的落值人不等于初审人**；对账前先读状态机代码确认列语义，避免把设计当缺陷。

### 5.2 历史脏数据：孤儿审批 todo 与超管域脏单

- **现象**：全局待办清零时发现两笔残留——CC…005 业务单早在 B19 前经旧退卡审核链路被驳回（history 仅 SUBMIT，todo 成孤儿）；RF…002 storeCode=null（超管域脏单），门店/区域账号均不可见。
- **处理**：RF…002 用 E014 admin token 走正规驳回链路置 REJECTED；孤儿 todo AP…000005 无业务态可推，直接 PG UPDATE 置 REJECTED 并留痕说明。
- **教训**：审批中心与业务单状态机分表存储，旧链路/异常中断会产生孤儿 todo；批量验证收尾时以「approval_todo PENDING=0 + 业务单无悬挂态」为数据干净标准。

### 5.3 环境与工具备忘

1. **审批列表响应格式**：`GET /api/txn/approval?tab=todo` 返回**裸 JSON 数组**（非 {data:[]}），脚本解析须兼容 `d if isinstance(d,list) else d.get('data',[])`。
2. **PG 表名/列名**：退款表 `txn_refund`、退卡表 `txn_card_cancel`（主键列均为 **txn_no**）；划扣任务表 `writeoff_desk_task`（wd_no/reviewer_id）、划扣记录表 `writeoff_record`（sign1/sign2）；人员表 `staff`+`staff_role`（无 org_staff）。
3. **prod 登录**：端点 `/api/org/auth/login`（非 /api/auth/login），字段 loginName；SE/SST 工号仅 seed 存在。
4. **curl**：`--noproxy '*' -sk -H "Authorization: Bearer $TOKEN"`，URL https://localhost:18443（seed）/8443（prod）。
