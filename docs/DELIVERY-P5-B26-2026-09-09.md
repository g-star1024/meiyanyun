## 二、接口与状态契约

### 2.1 域⑦ 通知多渠道（txn-service，base `/api/txn`）
| 端点 | 方法 | 说明 | 权限 |
|---|---|---|---|
| `/notifications/stream` | GET(SSE) | 实时推送通知（替代轮询 /unread-count） | 登录即可（按 recipient 隔离） |
| （内部）`NotificationFanoutJob` | 定时 | 每 60s 扫描未扇出通知，按 `notify_preference.channels` 逐渠道建 `notification_delivery` 并投递；INBOX 标记 SENT 并经 SSE 推送 | `@Scheduled` |
| （内部）`NotificationQuietConfig` | — | 免打扰全局配置（URGENT 不受限） | — |

- **投递状态机**：`PENDING → SENT / FAILED / SKIPPED / DEFERRED`（DEFERRED=免打扰时段延后，下一轮重试）。
- **幂等**：`notification_delivery` 唯一约束 `(notification_id, channel)` + NOT EXISTS 查询，保证同通知同渠道只处理一次，重启可自愈。
- **诚实投递**：SMS/WECHAT/EMAIL 适配器将消息 POST 到可配置 dev 网关（`meiyun.notify.gateway.*-url`，默认空）；**未配置网关返回 SKIPPED（绝不伪造发送成功）**。

|---|---|---|---|

### 2.3 域⑤ 外部渠道回传（marketing-service，base `/api/marketing/channels`）
| 端点 | 方法 | 说明 | 权限 |
|---|---|---|---|
| `/{channelCode}/callback` | POST | 各平台回传事件（CLICK/LEAD/CONVERSION）落库 | 公开端点，**默认 fail-closed 强制 HMAC 签名**（见下） |
| `/{channelCode}/callbacks` | GET | 按渠道列出回传 | marketing:view |
| `/callbacks` | GET | 全部回传（可按 status 过滤） | marketing:view |
| `/{channelCode}/sample` | GET | 返回联调样例（curl + JSON + 签名算法说明） | 公开 |

- **实体**：`channel_returnback`（channel_code / external_user_id / event_type / payload / status / sig_nonce 等）。
- **签名（fail-closed，运行态实测核实）**：`meiyun.channel.dev-no-auth` **默认 `false`**——未显式开启免签时，无 `X-Channel-Sig` 头一律 401；密钥未配置返回 503（而非放行）。签名串 = `hex_lower(HMAC_SHA256(secret, "{渠道码大写}\n{ts}\n{nonce}\n{rawBody}"))`，时间戳 ±300s 窗口、常量时间比较；白名单外渠道一律 401（不暴露渠道是否存在）；限流 60 次/分→429；`bizRef` 幂等去重。首版文档「默认 true 免签」的描述有误，以代码与冒烟为准（dev 联调如需免签须显式 `dev-no-auth=true`，本次冒烟全程未开启）。
- **种子**：`ChannelReturnbackDataInitializer` 在表空时灌 2 条样例（抖音转化 / 小红书线索），无需真实 OAuth 即可联调。

## 四、实现要点与口径（需你重点审核）

1. **通知免打扰实现偏离原假设**：调研发现 `NotifyPreference` 实体**实际无 quiet 字段**（与先前设想不同），故免打扰改由 **txn 全局配置** `meiyun.notify.quiet.*` 实现（INBOX 始终送达；非紧急的短信/企微/邮件在免打扰时段 DEFERRED 延后；URGENT 不受限）。如你希望把 quiet 字段补回 `notify_preference` 表，请告知，我可补一列 + 迁移（注意：该服务无 Flyway，将走 ddl-auto 自动补列）。
2. **短信/企微/邮件「诚实 SKIPPED」**：未配置 dev 网关时适配器返回 SKIPPED 并记日志，绝不伪造发送成功；真实运营商接入只需把 `meiyun.notify.gateway.*-url` 指向对应 webhook，不引入任何凭证/SDK。
3. **SSE 实时推送**：扇出 Job 在 INBOX 送达后调用 `NotificationStreamRegistry.push(recipient, notification)`，前端铃铛订阅 `/notifications/stream` 即可免轮询。未修改 ApprovalSlaJob（其落 notification 行后由扇出 Job 异步捕获推送）。
4. **赠金口径**：`grant_amount_fen` 单位「分」；满赠需 `threshold_fen>0`；过期按 `expire_months` 计算 `expire_at`；报表 `perCustomer` 仅统计 VALID 余额。`MANUAL` 发放 sourceBizRef 天然唯一，规则发放按 `(source_biz_ref, rule_id)` 幂等。
5. **外部渠道回传**：`dev-no-auth` 默认 **false（fail-closed）**，无签名一律 401、密钥未配 503；联调免签须显式置 true（本次冒烟全程保持 false 走真实签名链路）。回调体含 `customerId` 时先经客户目录硬校验，存在才标 `PROCESSED` 并回填 `matched_customer_id`；客户不存在直接 400 不落库（防归因污染）；无 customerId 标 `RECEIVED`。

## 六、冒烟期发现与处置

### 6.1 部署教训：权限变更必须重建 org-service 镜像并重登录（非代码缺陷）
- 现象：首轮发赠金 403「无操作权限：需要 grant:edit」。根因：JWT 权限在**登录时由 org-service 的 PermissionMatrix 签发**，业务镜像重建不影响已签发 token；当时 org-service 为 3 天前旧镜像。
- 处置：宿主机 `mvn -o -pl org-service -am package -DskipTests` 重新打 fat-jar → compose build org-service → **双栈** up -d 重建 → 等 45s healthy → 重新登录拿新 JWT，全绿。
