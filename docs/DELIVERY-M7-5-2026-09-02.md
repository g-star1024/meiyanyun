## 一、本阶段交付内容

### 1.1 数据域模型（meiyun-security 公共模块）

- `LoginUser` 扩展为 9 参 record：`(staffId, staffName, roles, storeCode, scope, perms, devLogin, region, stores)`，`isSuper()` 判定超管通配。
- JWT（HS256）claims 新增 `region` / `stores[]`，登录签发时由员工所属大区与辖区门店列表填充。
- `DataScope` 辅助器提供四类能力：
  - `current()`：取当前登录人；
  - `<T> Specification<T> storeSpec(String storeAttr)`：门店域列表注入（STORE 无店 → `cb.disjunction()` 零结果，不泄露）；
  - `<T> Specification<T> ownedSpec(storeAttr, ownerAttr)`：门店 + 归属人双维（SELF 域医生/咨询师只见本人数据）；
  - `canReadStore(storeCode)` / `canReadOwned(storeCode, ownerId)`：单条详情越权断言，跨区统一 404「数据不存在或无权查看」，不泄露存在性。
- 角色→数据域映射（ROLE_SCOPE）：SUPER_ADMIN=GROUP；REGION_MGR/FINANCE=REGION（FINANCE region=null+stores=null=明细全量）；STORE_MGR/DOCTOR/FRONT_DESK/OPERATOR=STORE；CONSULTANT=SELF。

### 1.2 各服务数据域注入（12 个业务类文件、22 处 Specification 注入、19 处详情断言）

| 服务 | 端点 | 注入方式 |
| ---- | ---- | -------- |
| txn | 预约列表/看板、订单列表/详情、核销列表/详情、会员卡、咨询方案、客户 360（orders/rfm/consultations/appointments）、复购、双签工单 | `ownedSpec("storeCode","doctor"/"consultant")` + `storeSpec` + 详情 `canReadStore/canReadOwned` 404 |
| txn | 现金日结 cash-settle | 自定义门店收敛：显式门店先 `canReadStore` 断言（越权 404）；STORE/SELF 强制本店、无店返空；REGION 逐店聚合；GROUP/超管全量 |
| finance | 营收 revenue | `storeSpec`（越权返空数组、财务全量）；prepay-pool/tax/accounts/outbox 为全局只读（设计如此） |
| customer | 客户列表/详情/卡/积分/标签 | `ownedSpec("storeCode","ownerStaffId")` + `canReadOwned` 404；name-map 为服务间匿名通道（无 @RequirePerm，设计内） |
| store | 门店列表/详情 | 内存 `canReadStore` 过滤 + 详情 404；name-map 公开 |
| org | 员工列表/详情 | 按 region/store 数据域收敛 |
| 12 个 Repository | — | 补 `JpaSpecificationExecutor` 以支持 Specification 动态查询 |

### 1.3 审批中心写动作细化鉴权（txn ApprovalService/ApprovalController/TxnService）

- **actor 一律收敛 JWT**：建单/审批/驳回/转交/加签的操作人全部取 `DataScope.current().staffId()`，请求 body 里的 `actor` 字段被忽略（伪造 `actor=E014/FAKE-ACTOR` 无效，审计与 applicant 均记录 JWT 登录人）。
- **状态机闸门**：退款/退卡建单按金额分级——L1（<¥5,000）直达 `stage=FINANCE`，L2/L3 起 `stage=REVIEW`；REVIEW 同意推进 FINANCE，FINANCE 同意终审 REFUNDED，任一阶段驳回→REJECTED（驳回原因必填，否则 400）。
- **阶段角色闸门** `guardStageAssignee`：登录 401 → 注解 @RequirePerm 403（无权限码）→ `canReadStore` 404（跨区）→ 阶段角色 403（REVIEW 须 STORE_MGR、FINANCE 须 FINANCE 角色，超管放行）→ assignee 403（已指派他人且非会签人）。
- **权限码事实**（PermissionMatrix 查证）：`refund:create` 仅 FINANCE + 超管；`refund:approve`/`cardcancel:approve` 授予 STORE_MGR 与 FINANCE；REGION_MGR 仅 `refund:view`（无 approve，注解层直接 403）。
- **待办服务端过滤**：todo tab「我的待办」= status=PENDING AND（assignee 空 OR assignee=我 OR coSigners 含我 OR applicant=我）AND 门店域；done/all 同样叠加门店域。

### 1.4 验证中发现并修复的真实缺陷（3 类、共 5 处）

| # | 缺陷 | 根因 | 修复 |
| - | ---- | ---- | ---- |
| 1 | **预约看板越权** `GET /api/txn/appointment/board` | 原直接调 native `boardStats(date, storeCode)`，前端可任意传 storeCode 拉他店统计，完全未接 DataScope | 改为显式 storeCode 先 `canReadStore` 404 + `ownedSpec("storeCode","doctor")` + 日期/门店谓词 + `findAll(spec)` 内存聚合 |
| 2 | **现金日结 500**（PG 42P18） | native SQL `and (:store is null or store_code = :store)` 参数未定型，PG 无法推断 `? is null` 的类型 | 改 `cast(:store as varchar)`；日期参数 `cast(:date as date)`（与 boardStats 范式一致） |
| 3 | **现金日结越权参数不拦截** | STORE/SELF 分支静默忽略前端 store 参数收敛本店，但响应回显伪造门店码，且与「显式他店→404」范式不一致 | 显式门店统一先 `canReadStore` 断言，越权 404 不泄露存在性 |
| 4 | **现金日结 STORE 无店查全量** | OPERATOR（storeCode=null）走 `cashSettleByDate(day, null)`，SQL 命中全部门店聚合，与 storeSpec 无店返空语义矛盾 | STORE/SELF 无店 → 返 `List.of()` 零结果 |
| 5 | **现金日结时区串日** | 容器 JVM/PG 会话均 UTC，`cast(signed_at2 as date)` 按 UTC 截断，北京时间凌晨 0–8 点工单被错算到前一天（查 8/20 返 8/21 凌晨单据） | 改 `cast(signed_at2 at time zone 'Asia/Shanghai' as date)` 按业务时区截断（避开 Hibernate 把 `::date` 误解析为命名参数的坑，用函数式 cast） |

## 四、遗留与风险

1. **服务层审计 actor 硬编码未清**（归 m7-8）：`AppointmentController.create` 等旧端点审计仍写 `"system"`（如 NO_SHOW 审计），M4Flow/M4Repurchase 部分写动作的 cmd.operator/consultant 尚未全面收敛 JWT 登录人；审批/退款/退卡新链路已全部收敛。
2. **PG 时区口径**：容器为 UTC，凡按 timestamptz 截日的原生 SQL 都须 `at time zone 'Asia/Shanghai'`；本次已修 cash-settle，m7-8 应全站扫同类 `cast(xxx as date)` 写法（boardStats 用纯 date 列无此问题）。
3. **Hibernate 原生查询 `::` 陷阱**：`::type` 转型会被命名参数解析器误判，原生 SQL 统一用 `cast(x as type)` 函数式写法。
4. **测试造单**：验证在 core 库新增 3 笔退款单（RF20260902-000001 REFUNDED / 000002 PENDING_REVIEW / 000003 REJECTED）及对应审批待办，属验证数据，保留并记录在案。
5. **后端种子两套口径**（承前）：源码 SE 系列 vs 运行库 E 系列，m7-9 统一核对。
