## 1. 营销域 — 阻断级（必须修，否则不可用或安全失守）

### P0-1 回调节点匿名可写 + 安全默认倒置 + 公网可达
- 现象：`ExternalChannelController.callback` 无 `@RequirePerm`；`dev-no-auth` 默认 `true`；网关 `/api/marketing` 已转发 → 任何人可无限灌 `channel_returnback`。
- 连带缺陷：即便关免签，签名也只是明文 `equals`（无 HMAC / 无防重放 / 密钥硬编码默认值）；无渠道码白名单；未复用本模块已有的 `RateLimiter`。
- 修法：默认 `dev-no-auth=false` + 缺密启动 fail-fast；改 HMAC-SHA256(body+ts+nonce) 校验时间窗与 nonce 去重；渠道码枚举白名单（DOUYIN/RED/MEITUAN，未知 400）；复用 `RateLimiter` 按 channelCode+IP 限流；限 body 字节。

### P0-2 grant:edit 权限点未注册 → 真实角色全 403
- 现象：`GrantController` 5 个写端点标 `grant:edit`，但 `org-service` `PermissionMatrix` 营销域只有 `coupon:edit/poster:edit/live:edit/asset:upload/m5settings:edit`，`grant:edit` 不存在 → 除通配 `*` 超管外全部 403。
- 修法（二选一）：① 在 `PermissionMatrix` 对应角色补注册 `grant:edit`（**需改 org-service 既有文件 + 种子 SQL + 前端权限点**）；② 复用已存在的 `marketing:edit` / `coupon:edit`。现状不可维持。

### P0-3 GR### 单号违反模块单号铁律
- 现象：`GrantService` 用 `count()+1` 内存自增、无 `synchronized`；并发同号主键冲突裸 500；删除后号回落；3 位仅到 1000；前缀 `GR` 与发券单号空间同名（审计/台账不可区分）。
- 修法：独立前缀 `GRR`，注入 `BizNoGenerator.next("GRR", like -> ruleRepo.findTopByRuleIdLikeOrderByRuleIdDesc(like)…)`；Repository 加 `findTopByRuleIdLikeOrderByRuleIdDesc`。

## 2. 营销域 — 重要级（应修）

- **I-1 手动发赠金不幂等**：每请求新 `UUID`，重试/双击重复发真钱；`IssueCmd` 不收客户端幂等键。需 `clientReqId` + 查重返回原记录；`(source_biz_ref, rule_id)` 中 `rule_id` 为 NULL 时 PG 唯一约束不生效，手工发放需非 NULL 占位或独立 `req_id` 列 + 唯一约束。
- **I-2 issueByRule 查重-插入非原子**：并发触发 `uk_cg_src_rule` 时 `GlobalExceptionHandler` 不翻 `DataIntegrityViolationException` → 裸 500。需 catch 后重查返回已有记录。
- **I-3 GrantExpireJob 事务边界与注释相反**：Service 标 `@Transactional` 整批一事务；Job 仅外层大 try-catch、循环内无单条 try-catch、无限批加载。应去方法级事务 + 循环内 `expireOne(id)` 单条事务 + 单条 try-catch + 限批（如 `findFirst500`）。
- **I-4 过期 Job 时区非 Asia/Shanghai**：cron 无 `zone`，容器 UTC → 实际北京 11:00 跑。应 `@Scheduled(cron="0 0 3 * * *", zone="Asia/Shanghai")` 或 compose 注入 `TZ=Asia/Shanghai`；cron 建议外置为配置项便于冒烟。
- **I-5 回调 customerId 无存在性校验即标 PROCESSED**：可写不存在客户，污染“已归因”数据。需接 customer-service 校验，不存在落 `RECEIVED` 并记 `matchNote`。
- **I-6 ChannelReturnbackDataInitializer 无 @Profile/开关**：生产首启灌 2 条假回传，进对账/监控且不清。应加 `@ConditionalOnProperty(name="meiyun.seed.channel-returnback", havingValue="true")` 或 `@Profile("seed")`。
- **I-7 PUT 更新规则漏算 priority**：只改优先级时 `changed=false` 不落库；审计 payload 漏 `priority`。需纳入 `changed` 比较并补审计。

## 3. 营销域 — 建议级 / 边界存疑

- `/sample` 匿名信息泄露（无 `@RequirePerm` 且公开，可探端点结构/示例单号）
- 回传无 `(channel_code, biz_ref)` 唯一约束，广告重试重复落库
- 回调 body 无大小限制（建议 64KB）
- `validateRule` 未校验 `applicableStores`（文档宣称“适用门店逗号校验”但代码无）
- `ACTIVITY/NEWCOMER` 带 `threshold` 落无意义值未拦截
- 审计：`new ObjectMapper()` 每次新建（提静态常量）；过期 `bizType=GRANT_ISSUE/action=EXPIRE` 语义勉强（建议独立 `GRANT_EXPIRE`）
- 列表/报表无分页（`List` 全量，与既有范式一致但容量风险）
- `toggle` 空 body 默认 `enabled=true`
- `report totalBalance` 内存累加（建议 SQL `sum`）
- 实体列长 `rule_id` 默认 255 vs `CustomerGrant.ruleId` length=16，统一 32 更稳

**边界存疑**：门店隔离见 §5-2。

## 4. 通知域（txn-service）— 阻断 / 重要 / 建议

### 阻断
- **D1 浏览器原生 EventSource 无法鉴权，SSE 不可达**：`NotificationStreamController` 仅认 `Authorization` 头，不支持 `?token=` 兜底 → 标准 `EventSource` 握手即 401，替代铃铛轮询的目的用标准前端 API 无法达成。修法：端点支持短时一次性 query token（`AuthInterceptor` 仅对该路径解析、仍须验签，勿入 public-paths 裸奔）；或前端用 `fetch`+`ReadableStream` 带 Bearer 自解 SSE。

### 重要
- **D2 PENDING 残行永久卡死**：先 `save PENDING` 再 `deliver`，崩溃/异常后该通知退出 `findUnfanned` 且 PENDING 不在重试集 → 残行死锁（卡 INBOX 则实时推送永久丢失）。需重试集加入 PENDING，或将 PENDING 落库与 deliver 合并为一次终态 save。
- **D3 多实例并发唯一约束冲突**：`NOT EXISTS` 与 `insert` 非原子，冲突中断整条渠道循环（单实例不触发，扩容即爆）。需渠道循环内 catch `DataIntegrityViolationException` 后 `continue`，或加 ShedLock。
- **D4 FAILED/DEFERRED 无限重试**：无上限、无退避、不区分 4xx（对照 `FinanceEventRetryJob` 有 MAX_RETRY=20→DEAD）。需引入 `maxAttempts`、4xx 直终态、DEFERRED 记 `nextAttemptAt`。
- **D5 外发 HTTP 占用全局唯一调度线程**：Spring 默认调度池 1 线程，`ApprovalSlaJob`/`FinanceEventRetryJob` 共用，最坏阻塞审批催办/资金重试。需独立 `ThreadPoolTaskScheduler` 具名 Bean 并在 `@Scheduled(scheduler=)` 指定。
- **D6 免打扰时区未定义**：`LocalTime.now()` 随容器 TZ，UTC 下窗口整体平移 8h。需 `meiyun.notify.quiet.zone`（默认 `Asia/Shanghai`）。

### 建议（D7–D11）
- D7 无偏好行默认渠道（仅 INBOX）与 SYSTEM 通知（INBOX+SMS）不一致，建议抽公共默认解析
- D8 `InboxChannelAdapter` 为死 Bean（Job 硬编码 INBOX 分支），建议删除或并入适配器路由
- D9 Registry 无 SSE 心跳；推送 payload 直接用 `Notification` 实体会泄露 `idemKey` 等内部字段，建议用 DTO 投影
- D10 `findUnfanned` 的 `NOT IN` 随表增长变慢，建议加 `fanout_done` 标志或限期扫描
- D11 每轮缺汇总 info 日志；短信/邮件真实接入时 `to=staffId` 需换成手机号/邮箱解析

**通知域达标项**：实体映射/唯一约束/状态非 ordinal、鉴权隔离（recipient 取 JWT 不伪造）、诚实 SKIPPED、超时（3s/5s）、事务边界范式复刻、Registry 并发安全、编译真实可对齐、无既有文件被改动的静态迹象。
