## §3 数据模型设计

### 3.1 新表 customer_merge（业务域，JPA 实体 + ddl-auto:update，不走 Flyway）

| 列 | 类型 | 说明 |
|---|---|---|
| merge_id | varchar(20) PK | `MG` + 8 位日期 + `-` + 6 位序号（当日 max+1，防重号铁律，synchronized） |
| master_id | varchar(16) NOT NULL | 胜方（Survivorship：创建时间最早，用户可手动换边） |
| merged_id | varchar(16) NOT NULL | 被合并方（单笔一个 merged，多单据多行——mock mergedIds[] 落地为逐行） |
| group_type | varchar(16) NOT NULL | POOL / SAME_STORE / CROSS_STORE（快照自候选对） |
| match_reasons | varchar(64) | 命中理由 CSV（PHONE / NAME_BIRTHDAY / DEVICE / IDCARD） |
| score | numeric(3,2) | 快照 0.95 |
| reason | varchar(512) | 人工填写的合并事由（前端确认弹窗传入） |
| status | varchar(16) NOT NULL | PROPOSED / REVIEWING / APPROVED / MERGED / REJECTED / NOT_DUPLICATE |
| idem_key | varchar(64) UNIQUE | 幂等键：前端 clientToken 或 `pairId:masterId` 服务端兜底 |
| requested_by | varchar(16) NOT NULL | 发起人工号 |
| approved_by | varchar(16) | 审批人工号（直接执行时=requested_by） |
| approved_at | timestamptz | 审批时间 |
| executed_at | timestamptz | 迁移执行完成时间 |
| created_at | timestamptz NOT NULL default now() | |

索引：(master_id)、(merged_id)、(status)。merged_id + status 联合部分唯一（同一 loser 只允许一条 MERGED）由服务层守卫，不建函数索引。

### 3.2 新表 customer_merge_snapshot（迁移明细快照，回滚/审计依据）

| 列 | 类型 | 说明 |
|---|---|---|
| id | bigserial PK | |
| merge_id | varchar(20) NOT NULL | 关联 customer_merge |
| table_name | varchar(32) NOT NULL | 被迁移子表名 |
| row_ids | jsonb NOT NULL | 本次从 merged_id 迁出的主键/行标识数组 |
| moved_count | int NOT NULL | 行数 |

另存 loser 合并前全字段快照一行（table_name='customer'，row_ids=[merged_id]，附 loser_before jsonb 列存全字段）。**本批只留痕不提供回滚端点（拍板 D5）。**

### 3.3 customer 表新增列（JPA @Column 自动补列，零 Flyway）

| 列 | 类型 | 说明 |
|---|---|---|
| merged_into | varchar(16) NULL | 被合并后指向主档案 customer_id；NULL=正常档案。**不加物理 FK**（同表自引用＋写入顺序问题，走逻辑引用＋读侧过滤） |
| merged_at | timestamptz NULL | 合并执行时间 |

读侧影响（全站 grep 整改点）：所有 customer 列表/搜索/点选接口增加 `merged_into IS NULL` 默认过滤（已合并档案不再出现于列表/搜索/建档查重）；单条详情接口可访问（360 留痕展示「已合并至 XXX」横幅）。**这是本批影响面最大的横切点，需全站扫（见 §8 风险 R1）。**

### 3.4 dismiss 留痕（NOT_DUPLICATE）

复用 customer_merge 表：status=NOT_DUPLICATE、master_id/merged_id 按 pair 两侧原样落（不迁移任何数据）、reason=用户填写的非重复理由。候选发现查询排除已落 NOT_DUPLICATE 的 pair（双向匹配 (A,B)/(B,A) 均排）。

## §4 合并执行引擎设计（六步范式落地）

### 4.1 执行时序（单事务 @Transactional，失败整体回滚）

```
executeMerge(mergeId):
 1. 行锁：SELECT ... FOR UPDATE 按 customer_id 字典序锁定 master + loser 两客户行（防并发合并同一对/链式合并）
 2. 守卫：loser.merged_into 必须 NULL；loser.anonymized_at 建议 NULL（已匿名化档案默认不可合并，拍板 D7）；
    master.merged_into 必须 NULL（已合并档案不可当主）
 3. 快照：loser 全字段 → customer_merge_snapshot；8 子表各行主键清单查询入快照
 4. 迁移（顺序按依赖无关性，逐个 UPDATE）：
    4a. customer_tag_rel：DELETE FROM customer_tag_rel WHERE customer_id=loser AND tag_id IN
        (SELECT tag_id FROM customer_tag_rel WHERE customer_id=master)  -- 消交集防撞 (customer_id,tag_id) 主键
        → UPDATE customer_tag_rel SET customer_id=master WHERE customer_id=loser
    4b. member_card / appointment / consultation / txn_order / writeoff_record / repurchase / push_record
        逐表 UPDATE ... SET customer_id=master WHERE customer_id=loser，各记 moved_count
    4c. 逻辑关联表 15 张（拍板 D4 通过后同法迁移）
 5. Survivorship 聚合回写 master：
    level = 较高档（member_level 阈值比较，只升不降）
    total_spend = master.total_spend + loser.total_spend（numeric 元）
    points = master.points + loser.points（bigint，CHECK>=0 恒满足）
    visit_count = master + loser
    过敏史/关注点/意向等 text 字段：master 为空取 loser，非空不动（不拼接防污染）
    last_visit 类由业务表自然驱动（无冗余列则不写）
 6. loser 处置：merged_into=master_id, merged_at=now()；status/name/phone 等一律不动
    （不动 phone：保留撞单证据链；读侧已按 merged_into 过滤，不再出现于查重）
 7. merge 行：status=MERGED, executed_at=now()
 8. 审计：audit_log biz_type=CUSTOMER_MERGE action=EXECUTE，payload JSON
    {mergeId, masterId, mergedId, groupType, movedCounts:{...}, survivorFields:{level,totalSpend,...}}
```

### 4.2 关键风险工程对策

- **tag_rel 撞键**：4a 两步法（DELETE 交集→UPDATE 差集），DELETE 行数并入快照与审计（被消掉的交集 tag 对 loser 而言随档案作废自然消失，master 侧已有同 tag 无损失）。
- **并发**：双行字典序 FOR UPDATE 防死锁；幂等键唯一索引兜底重复提交；状态机守卫 MERGED 终态不可逆。
- **部分失败**：单事务，任何一步异常整体 rollback，merge 行状态留 REVIEWING/APPROVED 不前进，可重试（重试走同一 idem_key 短路）。

## §5 API 设计（customer-service，路径契约 /api/customer）

| # | 端点 | 权限 | 说明 |
|---|---|---|---|
| 1 | POST /api/customer/merges | customer:merge | 发起合并：{pairId 或 customerIdA/B, masterId, reason, idemKey}→ 校验 pair 有效（双侧 canReadOwned＋未 dismiss＋未合并）→ 按审批规则直接 MERGED 或落 REVIEWING（拍板 D2） |
