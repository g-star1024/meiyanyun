## 0. 背景与范围（用户拍板的三决策）

### 0.1 批前现状（运行态核实）

B35 闭合「收款 → 赠金抵扣 VALID→USED」正向链路：收银台混合支付时 marketing `GrantService.deduct()` 按 FIFO 带锁扣减、写 grant_deduction DEDUCT 流水。但**逆向链路完全缺失**——退款终审（txn `TxnService.confirmRefund`）只做卡本金回加（customer-service）与资金 outbox 分录，**赠金段退款后赠金不复活**：USED 券余额永久为 0，客户赠金资产与门店负债同时虚减。

### 0.2 范围三决策（用户拍板，2026-09-12）

1. **联动范围**：仅链路①「付款回加」——退款终审事务内同步调用 marketing 逆向回加，远程失败整笔回滚（502，不扣款不记账）。链路②「满赠门槛追回」（退款致消费不再满足满赠规则时追回自动发放的赠金）、卡 gift_balance 退款 RF 不回补登记，均登记 Backlog 不在本批。
2. **过期券口径**：回加但**保持 EXPIRED**（余额恢复、状态不复活），过期资产不再重新可用，审计可追溯。
3. **部分退款分摊**：按 **赠金 → 卡本金 → 法币** 级联冲抵（RefundSplit 三段），即一笔部分退款优先冲销赠金段，依次向下。

### 0.3 资金口径原则

**赠金段退款不产生任何 finance_event 资金分录**——赠金是营销负债而非真实资金，退款时赠金回加仅动 marketing 账本；卡本金段落 RF-DEPOSIT/IN/balance，法币段落 RF-REFUND/OUT/{渠道}（冲红方向，复刻既有退款 outbox 口径）。

## 1. marketing-service：逆向回加核心算法（5 文件 +218/-0 域内）

### 1.1 GrantDeduction 实体 +origin_biz_ref 列

`GrantDeduction.java`：新增 `origin_biz_ref VARCHAR(64)`（DEDUCT 行原本只有 biz_ref=订单号；REFUND 行需要双锚点：**biz_ref=退款单号 RF（幂等键，uk_gd_ref_grant 唯一约束防重）**、**origin_biz_ref=原订单号 OD（累计封顶按原单聚合）**）。ddl-auto=update 现网自动加列（B41 Flyway 纳管时收录此列）。

### 1.2 仓储两查询（GrantDeductionRepository / CustomerGrantRepository）

- `findByBizRefOrderByIdAsc(...)`：按单号查扣减/回加流水（幂等判定取 REFUND 行）。
- `sumRefundedByOriginGroupByGrant(String originBizRef)`：JPQL `SELECT grant_id, SUM(amount_fen) ... WHERE change_type='REFUND' AND origin_biz_ref=:origin GROUP BY grant_id`——**同一起源订单的多张退款单累计封顶**（防部分退款超额回加）。
- `CustomerGrantRepository.findByIdInForUpdate(...)`：`@Lock(PESSIMISTIC_WRITE)` 按 id 集合锁券，FIFO 逆向回加防并发超加。

### 1.3 GrantService.refund() 算法（[GrantService.java:332](file:///Users/huluobo/WorkBuddy/2026-08-15-23-51-02/meiyun-platform/backend/marketing-service/src/main/java/com/meiyun/marketing/GrantService.java#L332)，约 145 行）

1. **RF 幂等**：按 refundNo 查既有 REFUND 流水，命中则原样返回（refundedFen/grantCount/balanceFen 同首次），不双加；
2. **可逆额计算**：取原单全部 DEDUCT 流水 → 按 grant 聚合扣减总额 → 减同 origin 历史 REFUND 累计 = 各券可回额度；
3. **累计封顶**：本次申请额 > 可回总额，中文 422「原订单可回赠金不足：可回 X 元，本次需回加 Y 元」（**在锁券前拒绝**，不持锁等远程）；
4. **悲观锁 + 逆向 FIFO**：锁定涉及赠金（按到期倒序，后扣的先回），逐券回加直到回满；**USED 且未过期 → VALID 复活；EXPIRED → 余额回加但状态保持 EXPIRED**；
5. **写流水**：每券一条 REFUND 流水（biz_ref=RF、origin_biz_ref=OD、balance_after_fen、operator）；saveAll 唯一约束冲突时重查走幂等返回（并发双提交兜底）；
6. **审计**：GRANT_REFUND/ORDER（actor=system，payload 含 operator 真实操作人、grantCount、refundedFen、balanceAfterFen）。

### 1.4 内部端点（InternalGrantController:47）

`POST /api/marketing/internal/grants/refund`，`@RequirePerm("internal:grant-write")` + X-Internal-Token 服务间鉴权（不对外）；RefundCmd(customerId, amountFen, orderNo, refundNo, storeCode, operator)，返回 bizRef/refundedFen/grantCount/balanceFen。

## 2. txn-service：终审事务内级联（3 文件 +94/-43）

### 2.1 FinanceEventPublisher.RefundSplit 三段拆分（FinanceEventPublisher.java:140）

`refundSplitForOrder(orderNo, refundAmt)` 查原单 order_payment 按支付方式聚合实付：
- grantPart = min(原单 grant 实付, 退款额)，扣除后余额下传；
- balancePart = min(原单卡本金实付, 余)；
- cashPart = 余数（法币，按原渠道 wxpay/cash 等拆分多笔）。

txn 远程联动金额与 outbox 资金分录**共用同一口径**，杜绝「回加的钱和记账的钱对不上」。`emitRefundConfirmed` 空命令列表跳过（纯 grant 段退款不产生资金事件）；退款渠道集合显式排除 grant。

### 2.2 TxnService.confirmRefund 级联顺序（TxnService.java L294-331）

终审 RF 分支，单一 `@Transactional` 内：
1. 状态守卫（仅 PENDING_FINANCE 可终审，重复终审 400）；
2. `String actor = currentActor()`（JWT 工号，无 SecurityContext 回落 system，**请求体 actor 字段刻意忽略**——与该服务全部写操作口径一致）；
3. refundSplitForOrder 算三段；
4. **split.grant()>0 → grantClient.refund 先调**（营销域 4xx 业务错误透传/5xx 转 502「赠金退款回加失败：无法连接营销服务…本笔操作已回滚，未扣款未记账」）；
5. **split.balance()>0 → cardClient.refundForOrder 再调**（顺序经 InOrder 单测固化）；
6. 全部远程成功后才置 REFUNDED、save、写 CONFIRM 审计（payload 含 from/to、grantRefund/balanceRefund/cashRefund 三段金额）、emitRefundConfirmed 资金 outbox。

远程调用全在置态**之前**：任一失败异常抛出 → 事务回滚 → 单据停留 PENDING_FINANCE、卡回加不触发、无资金分录，可安全重试或驳回。

### 2.3 MarketingGrantClient.refund（:63）

复用既有私有 post()（RestTemplate + X-Internal-Token + 超时）：4xx 透传营销域中文 message（累计封顶 422 直达财务界面），5xx/IO 异常转 502 回滚文案。
