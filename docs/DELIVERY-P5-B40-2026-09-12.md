## 0. 背景与范围

### 0.1 起因

B36 营销资产对账时发现 meiyun_core 正式库存在种子门店 SST01 的海报投放与核销流水。B39 闭合后专项排查：首次清理 55 行幽灵主数据并加了门控代码，但容器仍跑旧 jar，force-recreate 后 55 行被重播——暴露出「门控只存在于源码、不存在于运行镜像」的真实缺口。本卡目标：**全库确认 SST 脏数据边界、根治重播源、安全处置存量、运行态实证闭环**。

### 0.2 范围四决策（自主采纳，沿用既有治理口径）

1. **根治手段**：三个漏网播种器补 meiyun_seed 门控（范式取自既有 CouponWriteoffDataInitializer），不改数据源、不拆库；

## 3. 踩坑链：stale jar 与字节码核验

1. **现象**：门控源码已提交，compose force-recreate 后 55 行幽灵数据依旧重播；
2. **根因**：backend/Dockerfile 只 `COPY backend/<svc>/target/<svc>-1.0.0-SNAPSHOT.jar`（宿主 fat-jar），此前一次 `mvn package -q` 无输出、jar mtime 未变，镜像里始终是旧 jar；`docker restart` 更不会换镜像；
3. **可靠核验方法**：`mvn -pl store-service clean package -DskipTests`（BUILD SUCCESS 8.1s，jar mtime 更新，47,286,416 字节）→ 解压 fat-jar `BOOT-INF/classes` → `javap -c -p` 对三个类 grep `meiyun_seed` **各命中 1 次**，门控确在新 jar 字节码内（macOS `strings` 对 .class 假阴性，不可用）；
4. 之后才 `docker compose -f docker-compose.app.yml build store-service` + `up -d --force-recreate`。
