## 0. 背景与用户拍板的三项决策

B18/B26 已把「发赠金」侧做真（GrantRule 规则 CRUD、customer_grant 账本 VALID/EXPIRED/USED、GrantExpireJob 过期批处理、手工发放端点与报表），但**赠金只能发、不能花**——收银台没有任何途径选择赠金支付，customer_grant 余额永远停在 VALID。B35 闭合的正是 B26 移交的下游写链路：收银台选赠金 → 跨券 FIFO 扣减 → 余额扣完转 USED → 流水/审计/对账。

范围定稿时用户拍板三项（均为白天窗口经 AskUserQuestion 确认）：

1. **UI 形态 = 支付方式增一项**：在收银台既有支付方式磁贴网格中增「营销赠金」磁贴，复用既有图标与选中态样式；不做独立弹层、不改 `<template>`/`<style>`。
2. **余额不足处理 = 本批做混合支付**：赠金可只付一部分，不足部分用微信/现金等其他方式补收；一单允许多笔支付，但赠金仅限一笔（首笔）。
3. **造数方式 = 走真实端点造数**：测试赠金与订单全部经网关真实 API 产生，不直接写库造数。

## 1. 方案要点

### 1.1 后端 marketing-service：扣减账本与内部端点

- 新增 `grant_deduction` 扣减流水表（实体 `GrantDeduction` + 仓储），列：`id, amount_fen, balance_after_fen, biz_ref（锚订单号）, change_type（DEDUCT/REFUND 预留）, created_at, customer_id, grant_id, operator, store_code`；`biz_ref` 唯一约束承担幂等。
- `CustomerGrant` 增 `USED` 状态流转：某笔赠金余额扣到 0 即 VALID→USED（部分扣减仍 VALID）。
- `GrantService.deduct(customerId, amountFen, bizRef, storeCode, operator)`：
  - **幂等**：先按 bizRef 查既有流水，命中直接返回（同单重放不双扣）；`saveAll` 撞唯一键再回查一次兜底并发；
  - **FIFO**：`findUsableForUpdate`（`FOR UPDATE` 悲观锁，按到期时间早→晚）取出全部有效赠金，逐笔 `min(剩余待扣, 该券余额)` 分摊，跨券扣减；
  - **超额拒绝**：可用总额 < 本次抵扣额直接 **422** 中文「赠金余额不足：可用 X 元，本次需抵扣 Y 元」，**不做部分抵扣的隐式兜底**（要么前端按真实余额提交混合支付，要么明确报错）；
  - 每笔分摊写一条 grant_deduction（balance_after_fen 留痕），customer_grant 余额递减、归零置 USED；
  - 审计 `GRANT_DEDUCT` / biz_type `ORDER`，payload 合法 JSON（customerId/storeCode/operator/amountFen/grantCount/balanceAfterFen），actor 为 system、真实收银员工号在 operator 字段留痕。
- 新增 `InternalGrantController`（`/api/marketing/internal/grants/balance|deduct`）：
  - 仅服务间调用，**X-Internal-Token 鉴权**（拦截器为内部令牌注入 perms，端点挂 `internal:grant-balance` / `internal:grant-write`，普通登录人即使拿到路径也 403）；
  - 网关层对 `/internal/**` 一律 404，不暴露外网；
  - deduct 返回 `{bizRef, deductedFen, grantCount, balanceFen}`。

### 1.2 后端 txn-service：收银台接入

- `PaymentService` 支付方式枚举增 `grant`：
  - 散客单（order.customer_id 为空）走 grant 支付 → 中文 **400**「散客订单不可使用营销赠金」；
  - 同一订单第二笔 grant 支付 → 中文 **409**（赠金仅限一单一次，防拆单绕过超额校验）；
  - 调 `MarketingGrantClient.deduct`，营销域 4xx 中文 message **原样透传**（如余额不足 422）；5xx/网络异常统一 **502** 并明示「本笔操作已回滚，未扣款未记账」，防收银员误判；
  - 幂等键 bizRef = 订单号（与 grant_deduction 唯一约束对齐）。
- `M4FlowController` 增 `GET /api/txn/order/{no}/grant-balance`：
  - 权限 **`cashier:view`** 而非 marketing 域权限——收银角色 FRONT_DESK（E006）只有收银/客情权限、无 `marketing:view`，直读营销域会 403；故经交易域转发鉴权；
  - 散客或营销服务任何异常 → 降级返回 `{customerId, balanceFen:0, available:false}`，**不阻断正常收款**（收银员可改用其他方式）；正常返回 `{customerId, balanceFen, available:true}`。
- 新增 `MarketingGrantClient`（RestTemplate）：`marketing.service.url` 配置化（默认值仅本地单测用）、内部令牌走配置、4xx 透传/5xx 与连接异常分别 502 中文。

### 1.3 前端：OrderView script 适配层（`<template>`/`<style>` 零改动）

git diff 实证：`OrderView.vue` +57 行全部在 `<script setup>`，模板与样式 0 行变更。7 处改动：

1. `api/order.ts` 增 `GrantBalanceDTO` 与 `getOrderGrantBalance(no)`（走 `/txn/order/{no}/grant-balance`）；
2. `PayMethod` 类型增 `'grant'`；
3. `PAY_METHODS` 增磁贴 `{ key:'grant', label:'营销赠金', icon:'finance', desc:'赠金抵扣' }`，METHOD_LABEL 增中文名；
4. 切换订单时重置 grant 余额/可用状态；
5. 新增 grantBalance/grantAvailable/grantLoading 三 ref 与 `loadGrantBalance`（选中磁贴时查询；不可用/零余额/有额度三种 toast 文案）；
6. `pickMethod` 选中 grant 即查余额并 toast「该客户可用营销赠金 ¥X，不足部分请用其他方式补收」；

混合支付完全复用既有「一单单笔支付→部分收款→可继续收第二笔」的订单模型：赠金支付成功后订单回到待收款态、横幅显示已收/待收，第二笔选微信补差额即可，KPI/明细/tab 计数沿用既有 `await load()` 刷新联动，无需新增任何联动代码。

### 1.4 基础设施附修（真实运行缺陷）

联调首笔 curl 即暴露：txn-service 按 `MarketingGrantClient` 默认值 `http://127.0.0.1:8088` 在**自身容器内**找营销服务，Connection refused。根因是 `docker-compose.app.yml` 公共环境锚点漏配 `MARKETING_SERVICE_URL`（Spring 松散绑定映射 `marketing.service.url`）。补：

- `docker-compose.app.yml`：`MARKETING_SERVICE_URL: "http://marketing-service:8088"`；
- `docker-compose.seed.yml`：`MARKETING_SERVICE_URL: "http://meiyun-seed-marketing-service:8088"`。

教训：新增服务间 RestTemplate 客户端时，`@Value` 默认值只够本地单测，compose 环境变量必须随卡同步，否则要到真实跨容器调用才暴露。

## 2. 后端设计

### 2.1 真实表结构（information_schema 实测列名）

`grant_deduction`：`id, amount_fen, balance_after_fen, biz_ref, change_type, created_at, customer_id, grant_id, operator, store_code`（金额一律 bigint 存分，铁律 2；注意类型列叫 **change_type** 不是 biz_type）。

`order_payment` 真实列：`payment_id, cash_tendered, change_amount, created_at, operator, order_no, paid_after, pay_method, posted_amount`（注意是 payment_id/pay_method，不是 payment_no/method）。

审计表 `audit_log`：`id, biz_type, txn_no, actor, action, payload(jsonb), prev_hash, cur_hash, created_at`（哈希链沿用既有机制，GRANT_DEDUCT 入链不断链）。

### 2.2 涉及端点

| 端 | 方法/路径 | 权限 | 说明 |
|---|---|---|---|
| marketing | GET `/api/marketing/internal/grants/balance?customerId=` | internal:grant-balance（X-Internal-Token） | 可用余额合计（分） |
| marketing | POST `/api/marketing/internal/grants/deduct` | internal:grant-write（X-Internal-Token） | FIFO 扣减，幂等键 bizRef=订单号 |
| txn | GET `/api/txn/order/{no}/grant-balance` | cashier:view | 收银台查余额，散客/异常降级 available:false |
| txn | POST `/api/txn/order/{no}/payment`（既有） | cashier:create | payMethod 增 `grant` 分支 |

### 2.3 审计动作

- `GRANT_DEDUCT` / ORDER：营销域写，actor=system，operator 字段=真实收银员工号；
- 收款既有 `ORDER`/`PAY` 审计不变（actor=收银员）；
- 资金台账 `FUND_ENTRY`/`POST` 由 finance 既有入账链路写（grant 支付同样生成资金分录，与微信/现金走同一 FundEntry 入口）。

## 4. 已知缺口 / Backlog（已回写 ROADMAP）

1. **消费满额自动发赠金触发**：`GrantService.issueByRule()` 已就绪但当前**没有任何消费事件调用方**，发赠金仅手工 `POST /grants/issue`；CONSUME_THRESHOLD 规则不会在收款时自动触发。需在收款完成事件链挂规则匹配+幂等发放（可与 B25 自动积分 AUTOPOINTS 复用同一事件源），建议随 B37 营销规则引擎同期做。
2. **txn-service 扣减侧单测零覆盖**：grant 支付/Client/FIFO 联动目前靠 marketing 域 84 单测 + curl + 浏览器兜底，txn-service 本身无单测工程（全服务历史欠账）；散客 400/第二笔 409/降级 available:false/重放分支应补服务内单测防回归。
3. 赠金 REFUND（退款回冲赠金）：change_type 已预留 REFUND，但退款链路本批未接——若 grant 支付的订单发生退款，赠金是否退回、退回到原券还是新券，需业务定规则后实现。
