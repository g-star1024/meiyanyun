## 0. 背景与决策

B38（`6f2e734`/`2b03c46`）为 audit/marketing 两服务接通了全库共享 Flyway 版本链，但当时用户拍板范围只纳管 marketing_cfg + auto_grant_state 两张（V11），其余 **16 张营销属表仍靠 `ddl-auto=update`**。JPA update 的已知运行态风险（B32/B37 实证）：能加列、**不能加宽/改类型/补约束**，列宽缺陷只能现网手动 ALTER，且全新库结构只由实体注解决定、无书面基线。

本卡把 16 张表全部纳入版本链，设计决策（沿用 B38/V11 范式）：

1. **只做 CREATE TABLE IF NOT EXISTS 基线，不对存量表做 ALTER**。现网 16 表均已存在，迁移整体 NOTICE skipping，零数据风险；实体与现网不一致的缺列仍交 Hibernate update 兜底（本次 pg_dump 比对未发现缺列）。
2. **目标态按现网 pg_dump 物理结构 1:1 转写**，不按 JPA 实体「理想态」重画——保留现网真实的列类型、中文枚举 CHECK、无时区 TIMESTAMP、外键、注释、TEXT、唯一约束与索引，避免基线文档与运行态漂移。
3. **按条线分三批 V12/V13/V14**，单文件可读、失败域小；版本号接续共享链（B38 后下一可用 V12）。
4. **与 customer-service V3 的历史关系保持兼容**：coupon_template/coupon_grant/campaign 三张表的全新库 DDL 历史上挂在 customer-service 的 `V3__marketing_tables.sql`（DROP TABLE IF EXISTS + CREATE）。marketing 侧 V12 用 IF NOT EXISTS，两服务在全新库的执行顺序无论谁先都不冲突（见 §4 scratch 验证）。

## 1. 勘察事实

### 1.1 Flyway 多服务共享版本链

- 4 个 Spring Boot 服务各自持 `classpath:db/migration`、**不跨服务聚合扫描**，共享同一物理库 meiyun_core 的一张 `flyway_schema_history`，版本号全局递增互不冲突：
  - customer：V1/V2/V3/V5/V9
  - finance：V4/V6/V7/V8
  - audit：V10（out-of-order:true）
  - marketing：V11 + 本卡 V12/V13/V14
- V0 为 `baseline-version: 0` 虚拟基线行；`backend/db/migration` 为不上 classpath 的历史副本。
- marketing 配置：enabled、locations=classpath:db/migration、baseline-on-migrate、baseline-version 0、validate-on-migrate、`ignore-migration-patterns=*:missing,*:future`（只持本服务版本必须忽略他服务版本）；JPA `ddl-auto: update` 并存作净兜底。

## 2. 迁移内容要点

- 统一范式（仿 V11）：文件头注释（标题/版本号占用/背景/幂等时序）；`CREATE TABLE IF NOT EXISTS`；索引 `CREATE INDEX IF NOT EXISTS`；金额一律 BIGINT 存分；时间戳默认 TIMESTAMPTZ（唯 live_session.start_time 保留无时区）；序列主键 BIGSERIAL；仅全新库生效的约束内联在建表语句。
- V14 push_record 外键：
  ```sql
  CONSTRAINT push_record_customer_id_fkey
      FOREIGN KEY (customer_id) REFERENCES customer (customer_id)
  ```
  并 `COMMENT ON TABLE push_record IS '触达记录：每周每客户 ≤3 条（weekly_push_limit），发送前过违禁词校验';`
- push_record 的 FK 依赖 customer 表。customer 表由 customer-service 的 Hibernate 建出，**不在 customer 的 V1__init.sql 内**；docker-compose.app.yml 已固化 marketing `depends_on: customer … service_healthy`，生产全新库时序下执行 V14 时 customer 表必存在。

## 5. 结论与后续口径

- marketing-service 全部 18 张属表（V11 的 2 张 + 本卡 16 张）自此 **100% 纳入 Flyway 版本链**，结构有书面基线、全新库与现网同构。
- `ddl-auto: update` 本批**保留不动**（作为实体新增加列的净兜底）；后续可评估在确认实体与基线完全一致后由 `update` 改 `validate`，使结构漂移在启动期硬失败——登记为后续治理项，本批不做以免扩大范围。
- 本批无 Java/前端改动、无新增单测（纯 SQL 基线）；现网与全新库两场景均真验通过。
