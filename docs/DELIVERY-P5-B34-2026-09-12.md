## 1. 两卡方案要点

### 1.1 卡A 后端+前端：BOM 扣料异常缺料明细全链路贯通（commit `73e4b7c`）

改造前 `POST /internal/bom/deduct` 库存不足时只回一句纯文本失败信息，txn 侧把这句话整个塞进 `detail_json`，前端异常列表只能显示「库存不足」四个字——**运营看不到到底缺哪个耗材、缺多少**，必须去查库。本卡把缺料信息结构化贯通到页面：

- **store-service 抛结构化异常**：`ConsumableService` 库存不足时抛 `InsufficientStockException`，携带 `shortages[]`（`skuCode`/`skuName`/`needQty`/`stockQty`/`unit`）；`InternalBomController` 新增 `@ExceptionHandler` 转为 **HTTP 422** `{message, shortages[]}`。选 422 而非 400：这是「语义正确但业务前置条件不满足」，与参数校验失败（400）区分开，便于 txn 侧精确识别可解析的缺料响应。
- **txn-service 解析并落库**：`StoreConsumableClient.extractShortages` 解析 422 响应体还原缺料结构；`BomDeductService.registerFailure` 把 `shortages` 落进 `detail_json`，审计 payload 追加 `shortageLines` 字段（保持合法 JSON，铁律 6）；`BomExceptionController` 的 `GET /api/txn/bom-exceptions` 透出该字段。
- **附修 1 项运行态真实缺陷（两处同源）**：`BomDeductExceptionRepository` 与 `ProjectBomRepository` 的流水号生成 `substring(exc_id from N)` 起始位截错，导致**序号恒为 1 无法递增**。`exc_id` 格式为 `BEX` + `yyyyMMdd`(8) + `-` + 6 位序号，前缀共 12 字符，故序号起始位应为 **13**。ProjectBomRepository 侧属预防性同步修复（同一口径、同一类 BUG，当时未触发但必然复现）。
- **前端展示**：`api/bom.ts` 补 `shortages` 类型；`InventoryView.vue` 异常行追加缺料明细展示；`stores/bom.ts` 的 `loadBoms`/`loadExceptions` 补 `await ctx.loadStores()`——门店上下文未就绪时 `currentStoreCode` 仍是初始常量，会带着不存在的门店码发请求导致 404，此为对齐全仓既有惯例的修复。

### 1.2 卡B 后端+前端：券核销兜底门店配置化（commit `9a82af6`）

**问题（真实脏数据实证，非推测）**：`CouponWriteoffService` 硬编码 `FALLBACK_STORE_CODE = "SST01"`。集团/大区账号（JWT 内 `storeCode` 为空）执行核销时，这个编码被直接写进核销流水。而 core 库**根本没有 SST01 这家门店**（该编码只存在于 seed 库），导致：

1. `coupon_writeoff_record.store_code` 指向不存在的门店主数据；
2. `store_name` 因解析不到而退化成编码本身。

历史脏数据 `WR20260908-000004` ~ `000007` 四条流水的 `store_code` / `store_name` **双双为 "SST01"** 即为实证。

**改法**：

- **配置项落库**：`MarketingCfg` 新增 `writeoff_fallback_store_code`（varchar 32，可空），业务表走 ddl-auto=update 自动加列，**不写 Flyway**（铁律）。
- **写入前做门店存在性校验**：`MarketingCfgService.save()` 新增 `validateFallbackStore()`——填写的编码必须能在门店主数据中解析出名称，否则中文 400「兜底门店不存在：xxx，请从门店列表中选择」；`normalizeStoreCode()` 把空白归一为 `null`。**归一后的值参与 `changed` 判定与审计 payload**，保证「重复提交同值不产生冗余审计」。
- **`MarketingCfgDataInitializer` 刻意不回填该列**（仅加 Javadoc 说明）：留空即「未配置」的合法态；且 core / seed 两库门店编码体系不同（`ST-SH-00x` vs `SSTxx`），**任何播种值必然有一侧对不上**，播种反而制造新的幽灵码。
- **`CouponWriteoffService.currentStore()` 改为三级取值链**：

  | 级 | 取值来源 | 适用场景 |
  |---|---|---|
  | ① | `SecurityContext` 中本人所属门店 | 门店角色（如 E005 店长） |
  | ② | `marketing_cfg.writeoff_fallback_store_code` | 集团/大区账号，且已在营销设置中配置 |
  | ③ | 远程 `store-service /internal/first` 取门店表首家真实门店 | 集团账号且未配置 |
  | — | 三级均落空 → **抛 503** 拒绝核销 | 不再静默写入臆造编码 |

- **前端**：`/m5-settings`「审批流」分组新增「券核销兜底门店」下拉，选项来自 `storeContext` 的真实门店列表（首项为「未配置（自动取门店表首家）」），复用既有 `CSelect`；`m5Settings` store 六处同步（接口字段 / `DEFAULT_SETTINGS` / `adapt` / `FIELD_LABELS` / `save` / `payloadToChanges`），保证 dirty diff 与审计卡展开文案一致（空值显示「未配置」）。
