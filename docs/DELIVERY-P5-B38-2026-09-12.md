## 1. 卡1：audit-service 接入 Flyway + V10 基线（`6f2e734`，3 文件 +52）

### 1.1 pom.xml

在 spring-boot-starter-data-jpa 后新增（不写版本号，由 spring-boot-dependencies BOM 管理；运行态实测 Flyway Community Edition **9.22.3**）：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
```

### 1.2 application.yml

在 jpa 块（`ddl-auto: update` 保留）与 `meiyun:` 块之间插入 spring.flyway 配置，与 customer/finance 范式一致：

- enabled: true；locations: classpath:db/migration；table: flyway_schema_history；
- baseline-on-migrate: true、baseline-version: 0、baseline-description「JPA 自动建表基线」；
- validate-on-migrate: true；ignore-migration-patterns: `["*:missing","*:future"]`（四服务共享一条链，每个服务类路径只持有本域脚本，必须忽略他服务的 future 版本与历史缺失）；
- **额外 `out-of-order: true`**（marketing 及既有两服务均不开）——自主决策，理由见 §6.1。

### 1.3 V10__audit_log_baseline.sql

版本号取 V10：运行态核实 flyway_schema_history 中 V0–V9 已全部占位（V1/2/3/5/9=customer，V4/6/7/8=finance），V10 是首个空号。脚本头注释写明共享链取号理由（仿 V9__customer_automation.sql 范式），正文：

```sql
ALTER TABLE IF EXISTS audit_log
    ALTER COLUMN biz_type TYPE VARCHAR(32);
ALTER TABLE IF EXISTS audit_log
    ALTER COLUMN txn_no TYPE VARCHAR(128);
```

幂等设计的双场景语义：

- **现网**：两列早已是目标宽度，重设同宽为 no-op，迁移照常落 flyway_schema_history 完成补登；
- **全新库**：Spring Boot 启动顺序为 Flyway 先于 Hibernate ddl-auto，此时 audit_log 表尚不存在，`IF EXISTS` 令两条 ALTER 输出 `NOTICE: relation ... does not exist, skipping` 后正常继续；随后 Hibernate 按实体 @Column(length=32/128) 直接建出目标宽度，不会再产生漂移。

## 6. 自主决策记录

### 6.1 audit 额外开启 out-of-order:true（卡1）

共享链全局版本号的部署风险：若 marketing（V11）先于 audit（V10）上线，history 会出现 V11 已装、V10 未装的「空洞」，Flyway 默认拒绝乱序执行，V10 将永远无法补登（audit 启动直接报错）。audit 开 out-of-order 后，V10 可在 V11 之后乱序补执行；代价仅是启动一行可预期 WARN。marketing 作为当前最高版本持有者不需要此开关；customer/finance 未改动（其版本均连续，无补洞场景）。

### 6.2 V10 用 ALTER IF EXISTS 而非 CREATE TABLE 基线

audit_log 是跨服务写入的核心表，结构定义权历史上属于 JPA 实体（AuditLog.java 列远不止本批两列）。V10 不重建整表、只补登两条有明确手动 ALTER 凭据的列宽变更，最小化迁移职责；全新库场景显式让位 Hibernate 建表（IF EXISTS skipping），避免迁移与实体两张「结构事实源」分叉。

### 6.3 V11 仅纳管两表，不追求 18 表一次性全量

用户拍板范围即「marketing_cfg/auto_grant_state 纳入版本化」，两表是最近两批（B34 加列/B37 新表）亲手碰过、物理结构已逐列核实的表；其余 16 表规模大、部分历史脚本挂在 customer V3，一次性全量基线的核对成本与出错面不成比例。先接通通道、再按域分批（V12 起），每批均可独立真验。

### 6.4 重建策略：只 package + build 本卡服务，不 compose 全栈重建

全栈重建会重启 pg 并波及无关服务；两卡均只对目标服务 `mvn package` + `docker compose build <svc>` + `up -d <svc>`，其余容器（含 customer/finance/gateway）不动，他服务的重启幂等（轨③）通过受控的单次重启单独取证。

## 7. 踩坑记录：Dockerfile 复制宿主 fat-jar，compile 不产迁移镜像

卡1 首次只跑 `mvn -pl audit-service -am compile`（exit 0）即 build+up，容器虽 healthy 但 V10 未执行（日志无 Flyway 行、history 无 V10）。读 backend/Dockerfile 定位根因：镜像策略为 `COPY backend/${SERVICE}/target/${SERVICE}-1.0.0-SNAPSHOT.jar /app/app.jar`——**镜像内不运行 Maven，只复制宿主预构建 fat-jar**；`compile` 不产出 jar，target 下是旧包，镜像打进旧 jar。修复：宿主改跑 `mvn -pl audit-service package -DskipTests`（产出约 48MB fat-jar）后重新 build，V10 立即执行。卡2 起直接先 package 后 build，未再犯。此约定对后续所有改 pom/Java/迁移脚本的批次生效。
