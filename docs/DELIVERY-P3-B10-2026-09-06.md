## 一、目标与边界

### 1.1 目标

1. **项目配方（BOM）后台可配**：集团模板 + 门店覆盖两级，治疗项目 → SKU 清单 + 单次用量，库存页直接维护，不写代码、不重启即可调整。
2. **划扣双签 DONE 后自动扣库**：划扣单完成（afterCommit）自动按 BOM 扣减本店耗材库存，写带单位成本的出库流水；`bizRef = BOM:{writeoffId}` 幂等，重复触发/重试不双扣。
3. **失败登记可重试**：缺料等失败绝不阻断划扣（医疗红线），登记 `bom_deduct_exception`，库存页可见、可一键重试（补货后）、可手工核销。
4. **成本镜像入财务事件**：扣料成功向 finance 发 `CONSUMABLE_USE` 事件（只写成本镜像 TK-MATERIAL，资金红线），为 B11 月结成本结转备料。

### 1.2 边界红线

| 红线 | 落实方式 |
|---|---|
| **资金红线**：BOM 只产生成本镜像，绝不生成实付/收银 fund_entry | 事件类型 `CONSUMABLE_USE`，finance 侧落 fund_entry 固定 `subject=TK-MATERIAL / direction=OUT / source=ERP / ref_type=COST`；DB 实测 TK-MATERIAL 全部条目均为 ERP/COST，无 CASH/微信/支付宝实付分录 |
| **医疗红线**：扣料失败绝不阻断、不回滚划扣 | 扣料在划扣事务**提交后**（afterCommit）异步触发；store 侧 422/404 中文原因透传，txn 侧登记异常后划扣单照常 DONE |
| **无 BOM 项目静默跳过** | 未配配方的项目 `skipped=true`，不报错、不登记异常、不打扰前台 |
| 禁直读别域表 | txn→store 全部 RestTemplate + X-Internal-Token（`internal:consumable-write`），门店名富化走既有 ApptRefNameResolver |
| 权限 | 配方查看/异常查看 `inventory:consumable:view`；配方增改/异常重试核销 `inventory:consumable:edit`；内部扣料端点仅系统身份（perms["*"]）可调，普通登录人 403 |
| 数据域 | 门店角色只能看/写本店；集团模板（store_code 空串/GROUP）仅集团/品牌角色可维护，门店角色写集团模板返回中文 400 |
| 金额 | Long「分」；用量 integer；配方/异常业务表 JPA ddl-auto，种子不进 Flyway |

## 五、问题与教训

### 5.1 缺陷：afterCommit 回调中 JPA 写入静默丢失（本批最严重缺陷）

- **现象**：第一轮 E2E 中，扣料失败的异常单、扣料成功的成本事件偶发不落库；但划扣单正常 DONE、RestTemplate 审计调用全部落库。无异常抛出、无错误日志。
- **根因**：`TransactionSynchronization.afterCommit()` 回调执行时，原事务的同步状态仍为 active；回调内直接调 JPA Repository（默认 PROPAGATION_REQUIRED）会**加入那个逻辑上已提交的事务**，persist 随事务收尾被静默丢弃。而 RestTemplate 远程调用（审计、扣料）不参与本地事务，所以不受影响——这正是「审计有、落库无」的原因。
- **修复**（BomDeductService）：构造器注入 PlatformTransactionManager 建 `TransactionTemplate`（PROPAGATION_REQUIRES_NEW）：
  - 扣料成功分支：`txNew.executeWithoutResult` 包 emitConsumableCost + 既往 PENDING 异常自动核销；
  - 失败登记分支：整体 `txNew.execute` 包异常单落库（audit RestTemplate 留事务外）；
  - retry()/markResolved() 为控制器直调，保持 @Transactional 不受影响；
  - FinanceEventPublisher.emitConsumableCost 保持 REQUIRED（保护 B5 ApprovalService 同事务调用方）。
- **验证**：修复版 jar（acdfe936）重跑三场景——异常单 BEX…001 落库并可重试核销、CONSUMABLE_USE 事件 SENT、成本镜像 entry 11/14/17 全落库；回归冒烟 WO…0007 端到端全绿。

### 5.2 环境与工具备忘

1. **本机 Clash 代理拦截 localhost**：shell 存在代理（7890）时，`curl 127.0.0.1` 不加 `--noproxy '*'` 一律 HTTP 000；deploy.sh 脚本内 curl 未带该参数，**跑脚本前必须 `export no_proxy='*' NO_PROXY='*'`**，否则探活误报超时（产物实际已 cp 成功）。
2. **compose 重建容器回退镜像内旧产物**：deploy.sh 是 docker cp 热部署，镜像本身不含历次产物；Docker Desktop 重启/容器重建后必须重新跑 deploy.sh（可 --skip-build 推本地已验证 target/dist）。
3. **seed 栈容器名混杂**：部分容器带旧 compose 项目哈希前缀（`b4aaeb2bf0fd_meiyun-seed-store-service` 等），deploy.sh 的 container_of 只认规范名会报「容器未运行」；遇此情况手动 `docker cp <jar> <哈希名容器>:/app/app.jar && docker restart`（本批 store 即如此处理）。
