## 一、本批目标与边界

### 1.1 目标（DESIGN §9.1–9.3）

1. **三方对账**（§9.1）：`GET /api/finance/reconcile/tripartite?date=&storeCode=`（类级 finance:view，只读）。按日聚合三方——
   - **经营域**：txn 四流（订单收款 RF-REVENUE/IN、退款 RF-REFUND/OUT、卡扣划扣 RF-DEPOSIT/OUT+RF-REVENUE/IN 成对净额 0 仅计笔数、退卡 RF-REFUND/OUT 实退 + RF-DEPOSIT/OUT 冲预收 + RF-REVENUE/IN 违约金），经 txn 内部 finance-flows 系统身份取数，finance 侧按登录人 DataScope 逐行二次收敛；
   - **资金域**：finance fund_entry 当日 UTC 半开区间落账净额；MANUAL 期末成本录入（TK-* 科目，财务域自身动作）单列扣除后计差异；ADJUST 人工调平单列（adjustCount/adjustNetFen），不混入账账比对；
   - **现金方（账实）**：txn「现金交接」双签工单当日（Asia/Shanghai 自然日，signed_at2）实点现金合计，仅覆盖 cash 渠道；微信/支付宝/银行回单本期未接入，不臆造外部数字（红线⑤诚实降级）；现金方拉取失败时 `cashAvailable=false`，仅出账账结果、不做账实结论。
   - 输出分/元双金额、门店明细行（bizNet/postedNet/netDiff/unexplainedDiff/cash 各项 + matched）、汇总 matched 与中文 message。
2. **封账期间锁**（§9.2）：
   - `POST /api/finance/settlement`（finance:settlement:edit）：日结 DAY（period_key=yyyy-MM-dd）/ 月结 MONTH（period_key=yyyy-MM）× 门店封账；未来期间拒绝（日结≤今天 UTC、月结≤本月）；重复封账幂等重放（duplicated=true，不重复审计）；封账永久不可逆、无解封；快照 entryCount/netAmount（IN 正 OUT 负）；全审计 FIN_SETTLE（txn_no=`periodType:periodKey:storeCode`，payload 合法 JSON）。
   - `GET /api/finance/settlement`（finance:settlement:view）：封账台账，DataScope 逐行收敛 + 店名解析。
   - **闭期拦截**：FundEntryService.postOne 在幂等查重后、save 前调 SettlementService.isClosed（DAY/MONTH 双锁，occurredAt UTC 归一），命中已闭期间一律 **422** 中文拦截；ADJUST 调平分录 occurredAt=当前时间落当前期间，天然不撞闭期（差错调平通道始终可用）。
3. **网关加固**（§9.3）：Go 网关 `withInternalGuard` 包裹路由——外部流量访问 `/api/<service>/internal/**` 一律 **404 隐身**（不返回 401/403，不泄露端点存在性）；服务间调用在 compose 内直连服务名（*_SERVICE_URL 指向 service:port）不经网关，零误伤。

### 1.2 边界红线（本批不碰）

- 封账只阻断「新分录落入闭期」，不回溯修改既有分录（fund_entry 本就 append-only）；不提供解封/反封账。
- 账实核对仅现金渠道；微信/支付宝/银行回单自动导入列后续。
- 差异调平仍走既有 outbox DIFF → 人工 ADJUST 流程，本批不做自动改数。

## 五、问题与教训（归档必录）

### 5.1 🔴 连带缺陷修复：超管笔误门店码封账 200 静默产生永久垃圾锁行

- 现象：seed 验证中以 SUPER_ADMIN 对不存在门店 X999 发起封账 → **HTTP 200**，settlement_period 落入一行永久 CLOSED 垃圾锁（封账不可逆，无法清理）。
- 根因：`SettlementService.close()` 仅做 `DataScope.canReadStore(storeCode)` 数据域判定；而 DataScope 对超管/GROUP/BRAND 全域放行返回 true，**不校验门店是否真实存在**（DataScope 只回答「能不能看这个域」，不回答「这个码存不存在」）。
- 决策依据：封账永久不可逆 + 错误文案已承诺 404 + 资金安全反向失败即中止 → 必须补存在性校验。
- 修复：
  - `FinanceAggregationService.storeExists()`：调 store 服务 `GET /api/stores/name-map?codes=`（findAllById 只回存在门店）——**HTTP 200 且 Map 含 key = 存在；200 但缺 key = 确定不存在；调用异常（store 服务不可用/超时）= 服务故障**，抛 `StoreLookupException`。
  - `SettlementService.close()`：canReadStore 之后插入存在性校验——不存在 → **404**「门店不存在或无权操作该门店」；store 服务故障 → **503**「门店服务暂不可用，封账已中止，请稍后重试」保守中止，**不把服务故障误判为不存在、也不静默放行**（资金安全反向失败即中止）。
- 回归：X999 → 404 ✅；正常 SST01 封账 → 200 不受影响 ✅。
- 教训：**数据域授权（canReadStore）与资源存在性是两件事**；超管/集团角色全域放行后，不可逆写操作仍须独立确认资源真实存在；依赖外部服务做存在性判定时，必须区分「确定不存在」与「服务故障」两种信号，故障保守中止。
