## 1. 两卡方案要点

### 1.1 卡A 后端：五处置端点 + 三动作状态机 + 全动作审计（commit `f02384b`）

B30 的 customer_search_event outbox 只有 10s 中继 Job 单向搬运（SENT/RETRY/DEAD + 熔断降级 DB），ES 长期不可用时 retry_count 封顶的 DEAD 事件无任何人工出口；ES 恢复后也只能等中继轮询，无主动重放入口；无法投递的脏事件（已注销客户等）无法丢弃，永远占着失败队列。本卡补齐处置闭环：

- **新增 `CustomerSearchEventAdminService`（+262 行，单一处置组件）**：封装 retry / replay / discard 三动作状态机，全部走 @RequirePerm("customer:search:admin")、中文 400/404 拒绝、每动作合法 JSON 审计。
- **三动作状态机（与中继 Job 语义严格对齐）**：
  - **交回重试 `POST /{id}/retry`（MANUAL_RETRY）**：仅 **DEAD** 可执行 → status 回 PENDING、**retry_count 归零**、**last_error 清空**、回到中继 Job 正常消费队列；PENDING 幂等成功（不重复计数、不改字段）；SENT/DISCARDED 中文 400 拒绝。
  - **立即重放 `POST /{id}/replay`（REPLAY）**：PENDING/DEAD 均可执行 → **当场同步投递一次 ES**（复用与中继 Job 同一条投递链路）：ES 可用则置 SENT + sent_at；ES 不可用则保持 PENDING 走 RETRY 分支（retry_count 增长），返回中文提示「人工重放时 ES 暂不可用，可稍后重试」；SENT/DISCARDED 中文 400 拒绝。
  - **丢弃 `POST /{id}/discard`（DISCARD）**：PENDING/DEAD → DISCARDED，body `{"note":"..."}` trim 后 **≥2 个字符**（便于审计追溯，中文 400「丢弃原因至少 2 个字，便于审计追溯」），落 resolved_by（操作人）/resolved_at/resolve_note；SENT/DISCARDED 中文 400 拒绝。
- **读端点两连**：`GET /search-events`（status/customerId/eventId 过滤 + 真分页，**固定 event_id 倒序**，不接收任意排序字段防注入，Page 默认 20）；`GET /search-events/stats` 四键（pending/sent/dead/discarded 计数，LinkedHashMap 固定顺序）。
- **全量重建入口换权**：既有 `POST /api/customer/search/reindex`（B30 内部/运维口径）改挂 `customer:search:admin`，返回 `{"indexed":N}`，审计 REINDEX——处置台「全量重建索引」按钮由此获得受控人工入口。
- **事件实体扩 DISCARDED 终态**：CustomerSearchEvent 状态枚举加 DISCARDED + resolve_note/resolved_by/resolved_at 三处置字段（ddl-auto=update 自动加列，无 Flyway）。
- **两处运行态真实修复（同 commit）**：
  1. `GlobalExceptionHandler` 漏接 Spring `ResponseStatusException`——此前处置服务抛的中文 400/404 会被兜底异常处理吞成 500；补 @ExceptionHandler 透传 status 与中文 message。
  2. `audit_log.biz_type varchar(16)` 装不下新 biz_type `CUSTOMER_SEARCH_EVENT`（21 字符），ddl-auto=update 下 Hibernate **不会自动扩宽**（只加列不改列），实体 @Column(length=32) 与真实 DDL 不一致会写入截断/报错；实体改 varchar(32) 并经 ddl-auto 实际扩列（现存值均 ≤15 字符，无数据风险）。

### 1.2 卡B 前端：检索事件处置台整页 /search-events（commit `dbf8158`）

B30 交付时无任何处置 UI。本卡新增整页并挂进「客情洞察」菜单组：

- **KPI 四宫格**：待投递/已投递/投递失败/已丢弃，点击即按状态筛选（同态再点取消），与 stats 四键一一对应。
- **筛选条**：状态下拉（四态中文）、客户ID、事件ID（正整数校验，非正整数前端拦截不发请求）、查询/清除筛选；分页 CPagination（1 起页码）。
- **左表右详情双栏**（grid 1108px 380px）：左表行点击 selectedId 粉色高亮，操作列三文本按钮按状态机禁用（canRetry=仅 DEAD；canReplay/canDiscard=PENDING 或 DEAD）；右侧 sticky 详情卡全字段——状态/类型/客户/客户ID/手机/归属门店/重试次数/投递时间/人工处置记录/**last_error 红色错误块**，底部 交回重试·立即重放·丢弃 三按钮。
- **丢弃 modal**：`.modal-mask` + CCard + CTextarea，标题「丢弃事件 #N」，1 个字提交时**行内错误**「丢弃原因至少 2 个字，便于审计追溯」且弹窗不关闭；合法原因提交 → toast「事件 #N 已丢弃」→ 弹窗关闭 → 行翻已丢弃、三按钮禁用。
- **写后强一致刷新**：store `runAction` 每个写动作成功后 `Promise.all([list, stats])` 两连刷新（network 实测 reqid 严格配对）；reindex 后刷新 stats；所有写按钮 `v-perm.disable="'customer:search:admin'"`。
- **全量重建索引**按钮 → POST /reindex → toast「全量重建完成，共索引 100 位客户」。
- **路由/菜单/权限**：nav.ts 单一真源新增菜单项（icon alert、permission customer:search:admin、PAGE_TITLES），router 加 /search-events；无权限身份菜单自动隐藏，直访被路由守卫重定向 `/no-auth?from=/search-events&need=customer:search:admin`。

## 4. 疑点清单 × 自主决策

| # | 疑点 | 自主决策（默认） |
|---|---|---|
| 1 | retry 与 replay 如何区分 | retry=不投递只把 DEAD **交回队列**（rc 清零、清 last_error、回 PENDING，由 10s 中继 Job 按既有退避消费）；replay=**当场同步投递一次**（ES 不可用则保持 PENDING 走 RETRY）。两动作分别审计，UI 双按钮 |
| 2 | retry 对非 DEAD 状态如何处理 | PENDING 幂等成功（不计数不改字段，重复点击安全）；SENT/DISCARDED 中文 400 拒绝（终态不可回退） |
| 3 | replay 在 ES 不可用时的返回 | 不伪造成功：保持 PENDING（RETRY 分支，rc 增长），返回体/提示明确「人工重放时 ES 暂不可用，可稍后重试」 |
| 4 | 丢弃原因是否必填、多长 | 必填，trim 后 ≥2 个字符（1 个字无审计追溯价值）；前后端双重校验，中文 400 与前端行内文案一致；resolve_note 落库 varchar(256) |
| 5 | 处置权限码 | 新增 customer:search:admin，仅授 REGION_MGR（搜索失败处置影响全量客户索引，属区域/运维级，不下放门店）；reindex 同码收口 |
| 6 | 中继 Job 退避/熔断参数是否调整 | 不动：B30 的 10s 节奏/批 50/连续失败 3 次熔断 30s 全部保留，处置台只做人工旁路 |
| 7 | GlobalExceptionHandler 500 兜底问题 | 同卡补 ResponseStatusException 透传（否则所有中文 400/404 变 500），属本卡暴露的框架级真实缺陷，随卡修复不另开 commit |
| 8 | biz_type 列宽不够 | audit_log.biz_type varchar(16)→(32)，现存值 ≤15 字符无迁移风险；prod audit-service 旧 jar 择机部署（列已扩宽，旧值兼容，无运行风险），列 Backlog |
| 9 | 完成度如何计数 | 仪表盘按功能模块净增 2（后端处置闭环 + 处置台整页 ⬜→✅）；大表域② 仅新增「检索事件处置台」1 行（7✅→8✅），reindex/三动作/审计作为既有「客情登记（B30 实时写 ES）」行纵深增强只改备注，沿用 B30/B31 历史计数差口径 |
