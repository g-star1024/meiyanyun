## §2 现状盘点（全部真实库＋代码核实）

### 2.1 数据模型现状

- **staff_role**：仅 2 列 `(staff_id, role_code)` 联合主键（均 NOT NULL），**无 org_code / 生效区间 / 任何维度列**。现有 25 行 20 人兼岗：DOCTOR 5、STORE_MGR 3、FRONT_DESK 3、OPERATOR 3、REGION_MGR 2、SUPER_ADMIN 2、FINANCE 2、CONSULTANT 1、ROLE_GROUP_IT 1、ROLE_GROUP_OPS 1。
- **staff**：`role_code`（主角色 FK→role_def）、`region`（单值文本列）、`store_code` FK→store、status CHECK（在职/离职）。一个员工只能表达一个大区归属。
- **org_unit**：org_type CHECK（集团/区域/门店/部门）、parent_code **自引用 FK（全库唯一 FK 子表）**、store_code FK→store、leader_name 纯文本、status/inactive_reason。真实分布：**集团 1 / 区域 6 / 门店 23 / 部门 0**（B33 三写已交付但尚无部门数据），停用 0 行。
- **org_code 引用面**：全库无任何其他表持有 org_code / org_id / org_unit_code 列（information_schema 核实）——L38 引用检查范围极窄。

### 2.2 REGION 路由现状（三层口径一致：主角色 ∪ staff_role 并集）

| 层 | 代码点 | 机制 |
|---|---|---|
| 审批动作闸门 | ApprovalService.guardStageAssignee L714-740 | 读 JWT `roles.contains("REGION_MGR")`，不查库、**不校验大区匹配**（任何 REGION_MGR 可批任何大区单） |
| 转交/加签校验 | ApprovalService.guardTargetApprover L747-779 | OrgStaffClient→org `/internal/staff/{id}` 取 roles 并集，org 不可用 502 硬失败 |
| SLA 催办取人 | ApprovalSlaJob.resolveRecipients L151-177 → OrgController.internalStaffByRole L263-300 | REGION_MGR 传 storeCode→`regionOfStore`（org_unit 门店节点 region 列）解析大区→`staff.region` 等值过滤，失败软降级空列表 |

**缺口定性**：兼岗 REGION_MGR 的 org 归属只能靠 `staff.region` 单值碰巧过滤——「张三主角色店长（A 店），兼岗**华东**大区区域经理」在现有模型中无法表达；staff_role 命中后全大区通吃或被 staff.region 误杀。

### 2.3 SLA 现状（txn-service ApprovalSlaJob，唯一实现）

- 60s 扫描（fixedDelay，限批 50 条 FIFO）、超时置 `overdue=true`、催办节流 120min（`remind-interval-minutes`）、催办仅落 Notification（URGENT，link=/approval），idemKey=`SLA:{todoNo}:{recipient}:{round}` 幂等。
- **无升级动作、无自动代办、无手工催办端点**；assignee 机制（transfer/addSigner）已存在可复用。
- 阶段 SLA：review 24h / region 8h / finance 4h（`meiyun.approval.sla.*-hours`）。

### 2.4 层级写现状（OrgAdminController，无 Service 层）

- 三写端点：`POST /api/org/admin/org-units`（L40）、`PUT /{code}`（L110）、`POST /{code}/toggle-status`（L187），统一 `@RequirePerm("org:edit")`＋`@Transactional`＋审计。
- create 强制 `orgType="部门"`（L85）＋父必须=门店（L67-69）；update 仅部门可改 parentCode 且新父必须=门店（L156-164）。
- 数据域 `assertManageable`（L232-248）：集团/区域仅超管或 GROUP 域；门店/部门走 canReadStore——**放开层级写后数据域闸门已天然就位**。
- B33 收窄理由（DELIVERY-P5-B33 L154）：门店主数据有独立 store 域与开店流程，大区/集团调整属低频重大变更——本批放开但保留该边界（见 §6 D4/D6）。

### 2.5 删除现状

仅 toggle-status 启停；无物理删除端点；B33 明示「部门物理删除未开放，编码回收需人工介入」（DELIVERY-P5-B33 L157）。

## §3 数据模型设计（本批唯一 DDL）

### 3.1 staff_role 扩 org 维度（方案三拍板，推荐 B）

| 方案 | 结构 | 评价 |
|---|---|---|
| A | 主键不变 (staff_id, role_code)，org_code 普通列 | 一人同角色只能兼一个组织范围——「区域经理兼管华东+华北」无法表达，否决 |
| **B（推荐）** | **主键扩为 (staff_id, role_code, org_code)，org_code varchar(16) NOT NULL DEFAULT ''**（空串=全局兼岗，向后兼容） | 支持一人多区兼岗；PG 主键列不可 NULL 故用空串占位；现有 25 行回填 '' 语义不变 |
| C | 新建 staff_role_scope 子表 | 两表 join 改全部读点，过度设计，否决 |

迁移（单事务 DDL＋回填）：

```sql
ALTER TABLE staff_role ADD COLUMN org_code varchar(16) NOT NULL DEFAULT '';
ALTER TABLE staff_role DROP CONSTRAINT staff_role_pkey;
ALTER TABLE staff_role ADD PRIMARY KEY (staff_id, role_code, org_code);
-- 既有 25 行 org_code 自动落 ''（全局），行为与现状完全一致
```

不加 effective_from/to 生效区间（现状 25 行无需求，YAGNI，留 Backlog）。

### 3.2 L38 编码回收：org_code_tombstone 表

```sql
CREATE TABLE org_code_tombstone (
  org_code     varchar(16) PRIMARY KEY,
  org_name     varchar(64)  NOT NULL,
  org_type     varchar(8)   NOT NULL,
  deleted_by   varchar(32)  NOT NULL,
  deleted_at   timestamptz  NOT NULL DEFAULT now(),
  snapshot     jsonb        NOT NULL   -- 删除前整行快照
);
```

新建节点撞 tombstone → 409「该编码已于 xx 删除回收，不可复用」（防历史审计歧义）。**本批禁复用**，回收池管理（释放/重用）留 Backlog（D5）。

### 3.3 org_unit 不扩列

leader_name 维持纯文本展示（路由不依赖它）；层级写/删除复用现有列与 status/inactive_reason。

## §4 L36 · REGION 兼岗路由设计

### 4.1 取人路由升级（internalStaffByRole，SLA 催办与 L34 升级共用）

roleCode=REGION_MGR 且传 storeCode 时，命中口径从「主角色∪兼岗 → staff.region 等值」升级为：

```
主角色路径（不变）：staff.role_code=REGION_MGR AND staff.region = regionOfStore(storeCode)
兼岗路径（新）：    staff_role.role_code=REGION_MGR AND staff_role.org_code IN
                    ('', 大区 org_code, 门店 org_code)   -- ''=全局通吃
并集去重，仅在职
```

- 兼岗挂**大区节点**＝管该大区；挂**门店节点**＝仅管该店所属大区的审批（预备粒度）；org_code=''＝全局兼岗（现有 2 行 REGION_MGR 兼岗行为不变）。
- regionOfStore 解析失败（门店无 org 节点）→ 仅回落 '' 全局兼岗者＋staff.region 等值者，不留空。
- **2026-09-22 补记（方案 B 并集口径坐实＋授摘对称）**：同一员工两路径为**并集**——主角色命中（staff.region 等值）OR 兼任者范围命中任一成立即返回，消除 B87 卡1 实现偏差「按人互斥」（主角色命中只看 staff.region、else 才看范围行，致主角色者被授同角色范围行永不生效）；'' 口径细化——主角色双写的 '' 锚点行仅对**纯兼任者**（主角色≠role）计全局通吃，防主角色者借 '' 绕行；配套授摘对称——removeStaffRole 主角色拦截收窄到 orgCode=''（'' 锚点行仍 400，非空范围行可摘），T1StaffView 授侧放开主角色范围授予、摘除拦截对齐 row.orgCode===''。

### 4.2 转交/加签校验升级（guardTargetApprover）

org `/internal/staff/{id}` 返回体**新增 scopedRoles 字段**（`[{roleCode, orgCode}]`，staff_role 明细；原 roles 纯角色集保留兼容）。txn 侧 REGION 阶段校验：目标人 roles 含 REGION_MGR 且其 scopedRoles 中该角色 org_code ∈ {'', 本单大区, 本单门店}，否则 422「该兼岗区域经理不负责本单所属大区」。org 版本旧无 scopedRoles → 回落纯 roles 校验（兼容灰度）。

### 4.3 审批动作闸门（guardStageAssignee）

JWT roles 纯角色集无 scope（AuthController.rolesOf 登录解析，本批**不动**——不动登录链路即零会话风险）。**本批不收紧动作闸门的大区匹配**（D2），理由：列表可见性已由 DataScope 过滤，闸门收紧属权限语义变更应单独评审；本批只把「取人/指派路由」做准。

## §5 L34 · SLA 超时自动升级设计

在 ApprovalSlaJob.scanOne 超时分支后追加升级判定（复用现有节流与幂等骨架）：

- **触发**：overdue=true 且 remindCount ≥ `meiyun.approval.sla.escalate-after-reminds`（默认 2，即可配置轮次后升级），开关 `escalate-enabled`（默认 true）。
- **升级动作（每阶段）**：
  | 阶段 | 自动指派 assignee | 升级通知 |
  |---|---|---|
  | REVIEW | 该店 STORE_MGR（主∪兼，多人取 staff_id 最小者，确定性） | 该区域 REGION_MGR（§4.1 新路由取人） |
  | REGION | 该区域 REGION_MGR（新路由，同取最小） | FINANCE 全员 |
  | FINANCE | 不指派（财务已是末端） | 超管 |
- **通知**：Notification（URGENT，文案「SLA 超时升级：{todoNo} 已超时 {n} 小时并催办 {r} 次未处理」），idemKey=`SLA-ESC:{todoNo}:{stage}:{round}`，同 NotifyPreference 免打扰过滤。
- **自动代办边界（D3）**：本批只做「自动 assignee 指派＋升级通知」，**不做自动 transfer 过户**（过户改变责任人属业务强动作，留 Backlog 评审）。被指派者可按现有 transfer 手工转交。
- **审计**：audit_log 落 `SLA_ESCALATE`（payload JSON 含 todoNo/stage/assignee/notifyTo/remindCount）。
- 失败降级：org 取人失败（软降级空列表）→ 跳过指派仅落升级通知给超管，不阻断扫描批。

## §6 L37 · 门店/大区/集团层级写设计

复用 OrgAdminController 三端点放开（保持统一权限 `org:edit`＋事务＋审计＋assertManageable）：

| 规则 | 内容 |
|---|---|
| 父类型链 | 区域→父必须=集团；门店→父必须=区域；部门→父必须=门店（现状）；集团→parentCode 必须为空 |
| 集团节点（D6） | **禁 UI 新建**（全库仅 1 个集团，409「集团节点唯一」）；禁删（§7） |
| 门店节点 store_code（D4） | 新建门店节点**必须挂已有 store.store_code**（下拉选择，不新建 store 主数据——维持 B33「store 域独立开店流程」边界）；region 从父区域继承，storeCode/region 一致性校验（org_unit.region 须=父区域 org_name 对应 region 值） |
| 门店跨区移动（update parentCode） | 允许（区域间），连带更新本节点 region；**不级联改 staff.region / org_unit.store_code**，响应体带 `affectedStaffCount` 提示「该店 N 名员工 region 未随动，请至员工管理核对」 |
| 编码 | org_code 正则现状 `[A-Z0-9][A-Z0-9-_]{0,15}` 不变；撞 tombstone 409（§3.2） |

## §7 L38 · 物理删除设计

新端点 `DELETE /api/org/admin/org-units/{code}`，`@RequirePerm("org:edit")`＋`@Transactional`＋assertManageable：

**引用检查清单（任一命中 409 中文错误）**：

| 节点类型 | 检查 | 409 文案 |
|---|---|---|
| 任意 | org_unit 子节点存在（自引用 FK，唯一 FK 子表） | 「存在 N 个下级节点，请先处理」 |
| 门店 | staff.store_code=该店 且 status=在职 | 「该门店仍有 N 名在职员工，请先调整归属」 |
| 区域 | 子门店节点存在 | 同上子节点规则 |
| 集团 | 一律禁删 | 「集团节点不可删除」 |
| 部门 | 无其他 FK（全库核实无 org_code 引用）→ 仅查子节点 | — |

**删除执行**：DELETE 行 → 写 org_code_tombstone（含整行 jsonb 快照）→ audit_log `DELETE`（payload 同快照）。三动作单事务。
**边界**：不删 store 主数据（store 域独立）；不级联删/改 staff（拦截而非级联，防误伤）；已停用节点可直接删（inactive_reason 留 tombstone 快照）。
