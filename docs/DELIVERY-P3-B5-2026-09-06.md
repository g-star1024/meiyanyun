## 一、本批目标与边界

### 1.1 目标（DESIGN §8）

1. **耗材双签审批驱动库存扣减与成本落账**：门店耗材「入库 / 领用出库 / 报损出库」走 txn 审批流，按金额分级（L1 单签 / L2 双签 / L3 三签），审批通过后 store 侧扣减库存、移动均价滚算，txn 侧经 outbox 事件把成本推给 finance。
2. **finance 成本端点**：内部写入端点接收耗材成本事件，落 fund_entry（资金/成本流水）+ cost_allocation（成本分摊），并回填 revenue_monthly 的 cost、重算毛利与两率。
3. **前端去 mock + 财务三页持久化**：库存页（InventoryView）与财务预算/发票/设置三页（FinBudget/FinInvoice/FinSettings）从 mock 切真实 API；预算、发票、设置三类配置真正落库。
4. **§8.4 验收红线**：`vue-tsc` 0 error；毛利率异常（为负或 >100%）红色提示。

### 1.2 边界红线（本批不碰）

- **样式零改动**：前端只接数据/交互，不改视觉规范。
- **金额口径**：后端与写库一律 Long 分；前端展示元。
- **写接口四件套**：校验 / 幂等 / 审计 / 中文错误信息，缺一不可。
- **跨服务调用**：RestTemplate + `X-Internal-Token`，内部端点不经网关裸露。
- **建表分工**：业务表 JPA `ddl-auto=update` 自动维护；共享系统表（revenue_monthly 约束等）走 Flyway，**已执行迁移禁止修改**。
- **禁 SQL 伪造验证数据**：所有 seed 链路数据必须经真实 API/审批流产生，DB 只做只读核对。
- **G1（客户卡划扣联动 + 双账口径裁决 + 存量回填）不在本批**：经用户拍板随 B6 对账加固统一处理。

## 五、问题与教训（归档必录）

1. **chk_rate_sum 约束在零收入月误杀 → V6 迁移放宽**：原约束要求 cost_rate+gross_rate=1，但耗材成本先于收入落账（当月 revenue=0、cost>0）时两率无意义且不可能和为 1，导致 revenue_monthly 写入被 CHECK 拒绝。新增 `V6__revenue_monthly_rate_check.sql`：`CHECK (revenue <= 0 OR abs(cost_rate+gross_rate-1.000) < 0.001)`，**零收入月豁免**，chk_rev_balance 保留。FundEntryService 零收入月两率显式 0.000。**教训：费率类约束要先想清楚分母为 0 的边界月。**
2. **outbox DEAD 毒消息需人工复位**：FinanceEventRetryJob MAX_RETRY=20 后置 DEAD 不自动重试，避免坏消息无限打转；补偿/复位走人工核查。
3. **consumable 主表不存 qty**：库存余量在 consumable_stock（行锁防超扣），主表 cost_price 即移动加权均价；查表前先 `\d` 实证，勿凭命名臆测列。
4. **审批 tier 边界是分不是元**：L2_MIN=500_000 分 = 5000 元（曾误按 5000 分理解）；报损按申报金额分级、领用固定 L2。
5. **audit_log 列名实证**：关联键是 `txn_no`、操作人是 `actor`、payload 是 **jsonb**，**无 biz_id/operator/store_code 列**；审计 payload 必须合法 JSON（AuditService 写入前 canonicalize：TreeMap 排序 key + 紧凑序列化，应对 jsonb 落库 key 重排；时间截断到微秒防假性断链）。
6. **认证/审批路径以 Controller 实证为准**：登录是 `POST /api/org/auth/login`（字段 **loginName**，非 staffCode）；审批基路径 `/api/txn/approval`（单数），列表 `GET /?tab=pending`（非 /approvals、非 /todo）；客户域 `/api/customer`（非 /crm）。
7. **Flyway 共享库版本线**：全服务共用 flyway_schema_history，部署前先查最高版本（prod 原为 V5）；V6 已在双栈应用 success=t。
