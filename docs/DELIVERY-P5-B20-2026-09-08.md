## 五、问题与教训

### 5.1 通知中心从 mock 到真实：角标/列表/已读三者必须共享同一 store

- **现象**：初版铃铛角标在 CShellDesktop 组件挂载时各自 fetch，通知页已读后角标不刷新。
- **处理**：铃铛与通知页统一挂 notification store；openItem 跳转后乐观更新 items/unread，角标自动递减；markRead 失败回滚。
- **教训**：**跨页面共享的实时态（未读数）必须收敛到单一 store**，组件 onMounted 只 dispatch fetch，不各自持态。

### 5.2 SLA 催办的「双刃剑」：机制一上线，历史孤儿单立刻开始催办真人

- **现象**：prod 部署 SLA Job 后，首轮扫描就给财务（SE104/E012）发了 4 条 URGENT 催办——但其中两笔是 B3 期测试残留的孤儿 todo（业务单已 REFUNDED）。
- **处理**：孤儿 todo SQL 置 APPROVED 终态移出 PENDING 扫描集、孤儿通知置已读；正规在途单保留催办。
- **教训**：**定时催办类机制上线前必须先盘点 PENDING 存量**——机制无差别地对所有在途单生效，测试垃圾会被当成真实超时单催办到真人。后续批次上线类似 Job 前，先跑一遍 `status='PENDING'` 存量清单核查。

### 5.3 驳回路径也要清零 SLA

- **认知**：初读代码容易只关注 approve 办结路径；实测中专门用 UI 驳回 RF…000008 验证——REJECTED 同样 overdue=f/remind_count=0。
- **教训**：**所有终态（APPROVED/REJECTED）都是「办结」**，SLA 状态清零必须挂在两条路径上；本批已在 ApprovalService approve/reject 双路径落实并 E2E 实证。

### 5.4 环境与工具备忘

1. **前端端口协议**：seed 前端 18080 是 **HTTP**（HTTPS 仅网关 18443）；浏览器自动化开 `http://localhost:18080/`，开 https 会 ERR_SSL_PROTOCOL_ERROR。
2. **审批列表路径**：`GET /api/txn/approval`（**单数** approval，非 /approvals/todos）；返回裸 JSON 数组。
3. **notification 表列名**：收件人列是 **recipient**（非 staff_id）、级别列 **level**（非 severity）、已读列 **is_read**；通知表在 txn-service 库（meiyun_seed/meiyun_core）。
4. **txn_order 表**：无 customer_name/paid_amt 列（退款请求体的 customerName/paidAmt 仅入参不落订单表）；金额列 `amount` bigint 存分。
5. **internal 端点**：`/api/<svc>/internal/**` 被网关 withInternalGuard 拦截（外部 404），服务间直连需 X-Internal-Token 头。
6. **截图工具**：Chrome DevTools MCP take_screenshot 的 filePath 不能保存在工作区外（Access denied），省略 filePath 以附件形式返回。
