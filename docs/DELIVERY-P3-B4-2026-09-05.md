## 一、本批目标与边界

**目标**：让「储值」从账面数字变成有台账、可实扣、可对账的真实资金动作——

1. 客户域新增 `card_ledger` 储值流水台账（对齐 PointsLedger 样板），开卡/充值写 RECHARGE、余额支付实扣写 CONSUME、退卡写 REFUND，每笔带 `balance_after` 快照；
2. 新增开卡/充值端点（`customer:card:recharge` 权限，四渠道 **禁 balance**），充值联动 finance 落 RF-DEPOSIT/IN（资金流入预收池）；
3. 收银台 `payMethod=balance` 由「只记账不实扣」改为经 customer 内部端点**真实扣 member\_card.balance + 写 CONSUME 流水**，余额不足 422 中文拦截，跨服务失败整笔收款回滚（杜绝「订单收款成功但卡没扣」）；
4. txn 退卡终审（CC）联动 customer 回写（卡置「已退卡」、余额清零、REFUND 负额流水），失败整体回滚。

**边界（红线）**：

- 跨服务写只走内部端点（`X-Internal-Token` + 内部权限码 perms=\["\*"]），txn 不直连 customer 库、customer 不直连 finance 库；

- 金额后端一律 `Long` 分（充值/扣款 >0，CONSUME/REFUND 落账为负额），前端元；

- 写接口四件套：入参校验 / 幂等键唯一（充值 RC 单号、消费 orderNo、退卡 cancelNo）/ 全审计 / 中文错误消息；

- **充值不能用 balance**（不能用储值余额给储值卡充值），前端弹层剔除 balance 选项、后端再校验双保险；

- 部分收款**不发资金事件**：仅整单收齐（`paidAfter >= amount`）才 `emitOrderPaid`，收入一次性确认（详见 §五设计说明）；

- UI 模型 ≠ 后端能力处诚实降级；样式零改动。

### 3.4 curl 四条验收

1. **充值**：POST recharge 四渠道落 RECHARGE + member\_card.balance 增 + finance RF-DEPOSIT/IN + 账户镜像增，四处金额一致；
2. **幂等**：RC 单号重放返回既有充值单（实测语义为 **200 幂等返回、payment/ledger 不双写**，非 409），不双充；
3. **balance 实扣/余额不足**：POST /pay method=balance 带 cardNo，足额实扣写 CONSUME；超额返回 **422** `{"error":"BUSINESS_ERROR","message":"储值余额不足，当前余额 1800.00 元，本次需扣 3810.00 元"}`；
4. **退卡联动**：CC 终审 → card\_ledger REFUND 负额、卡置已退卡余额清零、finance 三分录平衡。

## 五、问题与教训（归档必录）

1. **Flyway 版本号按各服务独立版本线编排，共享库迁移先** **`\d`** **/ flyway\_schema\_history 实证**：customer 库初版迁移误用 V4（与既有版本线撞车），改名 **V5\_\_card\_ledger.sql** 后双库迁移成功；共享库（多服务同库）用 `ignore-migration-patterns` 容忍他服务迁移。教训：新增迁移前先查目标库 `flyway_schema_history` 已用版本。
2. **共享模块 / 多服务改动须根目录** **`mvn clean install`**：单服务 `package` 可能打入旧依赖 jar；本批 customer/txn fat jar 经 clean 全量构建（customer 48,427,534 字节、txn 47,363,828 字节，均 ≥20M 红线），前端 bundle `index-Cys2sdld.js`（283,605 字节）。
3. **compose env 重建顺序**：双栈部署涉及内部端点地址/token 的 env 变更时，须先重建依赖方容器再验活，避免旧 env 容器连旧地址。
4. **DB 列名以** **`\d`** **实证为准**：card\_ledger 变动类型列是 **`change_type`**（非 txn\_type），CHECK 约束 RECHARGE/CONSUME/REFUND/ADJUST；member\_card 无 card\_type 列（卡类型由 cardItem/totalTimes 表达）；txn\_order 无 customer\_name 列。写查询前先 `\d 表名`。
5. **部分收款不发资金事件（设计说明，非缺陷）**：PaymentService 仅在 `completed = paidAfter >= o.getAmount()`（整单收齐）时置「已收款」并 `emitOrderPaid`。部分收款时卡扣款实时落 card\_ledger + order\_payment（客户余额已真实减少），但收入分录待整单收齐一次性确认——避免一单多笔重复确认收入。浏览器实测 ¥1,800 部分扣款后 finance 无新行、收齐后才发 ORDER\_PAID，与设计一致。
6. **混合支付渠道口径（§4.1 用户已拍板）**：ORDER-PAID 分录金额取**整单应收** `o.getAmount()`（非各支付笔之和），channel 取 postedAmount **最大一笔** 的 payMethod，distinct payMethod>1 时 memo 追加「（混合支付）」；balance 部分另发一笔 RF-DEPOSIT/OUT（channel=balance）表预收转出。实测 alipay 201,000 > balance 180,000 → channel=alipay。
7. **Chrome MCP 参数格式**：take\_snapshot/click/fill/wait\_for 均必须带 **pageId**（先 list\_pages 取，seed 页=2）；wait\_for 的 text 必须是**数组** `["文案"]`；wait\_for 超时不代表操作失败（toast/跳转后 DOM 选择器未命中），须 take\_snapshot 实证页面真实状态——本批「全额后 ¥0 disabled」中断点即为过期快照假象，重新点击即正常。
8. **不得打印/物化凭证值**：内部 token/DB 凭据不落文档；seed 码系（SC\*/SST\*、SE\*、MC2026\*）与 prod（M\*/ST-SH-\*）不同，跨栈复验注意区分。

## 九、B4.1 高优补丁：含 balance 支付订单退款终审回加储值（G2 修复，2026-09-05）

> 用户拍板：G2 属**客户资金损失型缺陷**、改动集中在退款终审一条路径，先于 B5 修复；G1 留 B6。纯后端补丁，样式零改动。

### 9.1 缺陷与口径

**缺陷**：退款终审（RF 分支）原只发 RF-REFUND/OUT，不调 customer 回加卡——含储值余额支付的订单退款时，余额部分不回补储值卡（客户余额损失）；且 `refundChannel` 反查原单主渠道可能得 balance，把退款支出错记到 balance 渠道（资金未出商户却记流出）。

**修复口径（终审按 order\_payment 支付构成拆分）**：

- `balanceRefund = min(原单 balance 实付合计, 退款额)`——部分退款优先回加余额；`cashRefund = refundAmt − balanceRefund`（不为负）；

- 余额部分 → customer 回加卡（card\_ledger **REFUND 正额**，区别退卡清零的 REFUND 负额；bizRef=RF 单号幂等；order\_no 归集；按 CONSUME 流水反查扣款卡；防超退：累计回加 ≤ 原 CONSUME 扣款；卡非「在用」→ 422 中文转人工）+ finance **RF-DEPOSIT/IN/balance/ERP** 冲回预收池；

- 法币部分 → finance **RF-REFUND/OUT/CASHIER**，渠道仅从**非 balance** 收款流水反查（杜绝错记 balance）；

- 远程回加失败抛异常 → 终审事务**整体回滚**（退款单不置 REFUNDED），customer 以 RF 单号幂等，终审重试安全。

### 9.4 全站扫结论（B4.1 同类）

- txn→customer 卡联动调用点共三处，逆向路径全覆盖：收款 `consume`（PaymentService L139）、订单退款 `refundForOrder`（TxnService L268，本补丁）、退卡 `refundCard`（TxnService L298，B4 已具）；

- REFUNDED 状态转移唯一关口 `confirmRefund`（TxnController 终审端点 + ApprovalService 双签写回 L105 均汇聚于此），**无旁路退款**；

- **已知双跑口径差异（移交 B6，本补丁不动读侧以控制改动面）**：finance 读时聚合 [FinanceAggregationService.toRefundEntry](../backend/finance-service/src/main/java/com/meiyun/finance/FinanceAggregationService.java#L149-L157) 退款仍按全额单条 RF-REFUND/OUT 出账（未按支付构成拆 balance），与写侧 fund\_entry 双分录口径在「含 balance 的退款」上分叉——属 G1/B6「双账口径裁决」范畴，B6 ledger-diff 双跑会显式暴露该差异并统一裁决；

- **UI 手工退款表单不绑定原订单**：/refund 页「发起退款」自由文本建单（order\_no 为空、customer=C-NEW），`balanceRefundForOrder` 对空 orderNo 返回 0（纯法币退，行为正确）；订单关联退款（带 orderNo）当前仅 API 入口（RefundCmd 含 orderNo 字段，createRefund L83/resolveRefundStore 已支持）。前端「从订单发起退款并带 orderNo」的表单入口属体验增强，非本资金缺陷范围，记录待排期。
