## 1. 卡1：统一 marketing_cfg 读写 DTO 契约（`828ac6d`）

### 1.1 问题

- `GET /config` 直接序列化 JPA 实体 `MarketingCfg`，把 `cfgId` 与 B18  referral 时代遗留、M5-15 页面不用的 `referralArrivedReward`/`referralDealReward`/`commissionRate` 一并外泄；
- 读键名 `weeklyPushLimit`（对齐库列 `weekly_push_limit`）与写命令键名 `weeklyLimit` 不对称，前端保存时要做键名翻译，审计快照与视图键名也不一致；
- `defaultPushChannels`/`defaultAdChannels` 库内存 JSON **文本**，GET 出参是字符串，前端 `JSON.parse` 后才能渲染多选，POST 再 stringify——两端类型不一致；
- HTTP 视图通道与内部实体通道（核销兜底/推送频控/quota）共用同一个 `get()` 返回实体，外部契约绑架内部模型。

### 1.2 改法

`MarketingCfgService` 新增两个 11 字段记录（L297-308 / L316-327），**字段名与类型完全对称**：

- `ConfigCmd`（写）：`weeklyPushLimit(Integer)`、`quietHoursEnabled`、`quietStart`、`quietEnd`、`holidayExempt`、`largeCouponThresholdFen(Long)`、`pushRequiresApproval`、`approvalLevel(Integer)`、`defaultPushChannels(List<String>)`、`defaultAdChannels(List<String>)`、`writeoffFallbackStoreCode`；
- `ConfigView`（读）：同 11 字段；服务层把库内 JSON 文本解析为 `List<String>`，**读写两端同为数组**，前端不再 parse 字符串。

配套变更：

1. **周频键统一为 `weeklyPushLimit`**：废弃写命令旧键 `weeklyLimit`（破坏性变更，后端 Controller 绑定与前端 `marketing.ts`/`m5Settings.ts` 本卡同卡同步，无跨版本窗口）；
2. **视图物理剔除** cfgId / referralArrivedReward / referralDealReward / commissionRate 四个多泄列；
3. **保留内部 `get()`** 供券核销兜底门店、推送频控、quota 读取实体；HTTP 契约不再绑架内部实体通道；
4. **quota 独立契约刻意不动**：`GET /api/marketing/push/quota` 出参中的 `weeklyLimit` 是推送频控面板的既有前端契约（语义为「本周剩余/上限」），与配置写键不是同一命名空间，本卡不改；
5. **审计快照随写链改新键**：MARKETING_CFG 审计 payload 写 `weeklyPushLimit`；前端审计卡对 B37 前 **append-only 旧快照**中 `weeklyLimit` 键做**读时归一**（`m5Settings.ts` L281-285），diff 键映射同步（L295-305），历史审计展示不裂；
6. Controller GET 改返 `ConfigView`、POST 接 `ConfigCmd` 透传服务层；既有校验（周频硬约束上限 3、免打扰时段、兜底门店 B36 严格版 503/400 分层）全部保留。

## 2. 卡2：消费满额自动发赠金轮询 Job（`7552665`）

### 2.1 路径决策：轮询拉取而非 FUND_ENTRY 事件链路（自主决策，铁律 -1-C）

ROADMAP/Backlog 原文设想是「issueByRule 接 FUND_ENTRY 后事件」。勘察后改为 **5 分钟轮询 txn 拉取**，理由：

- B25 自动积分已落地 `AutoPointsJob` 轮询 txn `GET /api/txn/internal/paid-orders` 的成熟范式（X-Internal-Token、投影 DTO、故障分层均已验证），赠金自动发放复刻同范式可复用同一已支付订单事件源，无需新增事件投递链路与消费组；
- 幂等命名空间独立（积分 `AUTOPOINTS:` vs 赠金 `RULE:`），两 Job 互不干扰（见 `AutoGrantService` javadoc L20）；
- 支付链路（B35 刚闭合的 grant 扣减/混合支付）零改动，不增加支付主链路耦合与回归面。

### 2.2 组件（10 文件 +703/-1）

| 文件 | 职责 |
|---|---|
| `AutoGrantJob`（新增 45 行） | `@Scheduled(fixedDelay=300_000L, initialDelay=45_000L)` 串行调度防重叠，启动 45s 首跑 |
| `AutoGrantService`（新增 158 行） | 核心扫描/匹配/发放：窗口计算、规则筛选、逐单匹配、双层幂等、故障分层、双审计 |

| `AutoGrantState` + `AutoGrantStateRepository`（新增 57+8 行） | 单行游标表（state_id=1，ddl-auto 建表）记 last_run_at；首跑 NULL 自 **2000-01-01 UTC** 起全量回填 |

### 2.3 规则匹配口径

- 仅取 **CONSUME_THRESHOLD 且 ENABLED** 规则，按 `priority` **升序首条命中**——一单不叠多档（避免同单发多档赠金）；
- 门槛 `paidAmountFen >= thresholdFen`，**边界 `>=` 命中**（满 50000 分整的订单可获赠）；
- `applicableStores` 空白=全部门店；否则订单门店码须精确匹配；
- 跳过：CARD_SALE 售卡单（售卡不参与消费赠礼，与 B35 售卡禁令同口径）、空客户散客单、非正额订单；
- 发放复用 B26 `GrantService.issueByRule()`（账本、expire_at 规则有效期、idem_key 规范均复用），赠金 `expire_at` 按规则有效期计算（真验为 +3 月）。

### 2.4 双层幂等（资金安全核心）

1. **同规则重放层**：`idem_key = RULE:{ruleId}:{orderNo}` + `customer_grant.uk_cg_idem` 唯一约束——同一规则对同一订单永不重发；
2. **订单级跨规则锚点**：`existsBySourceBizRef(orderNo)` 校验——`idem_key` 只防「同规则同单」，若运营在两笔收款之间切换/新增规则，新规则对历史订单可能二次发放；source_biz_ref 锚订单号保证**一单最多发一次规则赠金**（与 priority 首条命中共同锁死）；
3. **游标窗口重叠**：窗口按 yyyy-MM-dd 日粒度、邻轮重叠（上界日整天会被相邻两轮重复扫描），重复单全部命中上述两层幂等，零新增。

### 2.5 故障分层（游标推进语义）

- txn 不可用（传输异常/5xx）或客户域 502：**整轮中止、不推进游标**，下轮从原窗口重试自愈；
- 客户不存在（客户域 400/空体）：**跳过该单、游标照常推进**（脏数据/跨域不一致不应卡死整轮）；
- CARD_SALE/空客户/非正额：跳过并推进。

### 2.6 审计

- 每笔成功发放复用 issueByRule 的 **GRANT_ISSUE/RULE 明细审计**（biz_ref=订单号，actor 在调度线程无用户上下文时回落小写 `system`）；
- Job 仅在本轮 `granted>0` 时补一条 **AUTO-GRANT/SYSTEM 汇总审计**（scanned/granted 计数），零发放轮不写噪声审计。

## 3. 附修跨域潜伏缺陷：audit_log.txn_no 列宽 24→128

真验过程中暴露的**既有跨域缺陷**（非本批新引入）：

- **现象**：规则明细审计号 `RULE:{ruleId}:{orderNo}`，实测 orderNo 形如 `OD20260912-000001`，整条 **40 字符**，而 audit-service `AuditLog.txnNo` 注解 `length=24`，现网列 `varchar(24)`；insert 触发 PG **22001 value too long**，audit-service 返回 500；
- **放大效应**：marketing 侧 `RestAuditRecorder` 对审计失败仅 `log.error` 不阻断主流程——结果是**赠金正常落账但明细审计静默丢失**。B35 手工发放号短（手工号/订单支付场景未超 24）从未触发，本批 RULE 锚点首次超长才暴露；
- **三处修复**：① `AuditLog.java` `@Column(length=128)`；② 现网 `ALTER TABLE audit_log ALTER COLUMN txn_no TYPE varchar(128)`（合规范式 `docker exec meiyun-pg psql -U meiyun -d meiyun_core -c "..."`，未使用任何内联凭据）；③ 本地基线 `db/schema.sql` 同步 varchar(128)（db/ 在 .gitignore 不入库）；
- **根因教训**：audit-service `ddl-auto=update` **不会加宽已有列**，且该服务无 Flyway——实体 length 变更对存量列无效，只能手动 ALTER。已扩记 Backlog：audit-service 需先引入 Flyway 并做全量基线；同次核实发现 `db/schema.sql` 中 `biz_type` 仍 varchar(16) 而实体/现网 B32 已 ALTER 为 32 的历史漂移，留基线批校准（本批不顺手改，避免夹带）。

## 6. 自主决策说明（铁律 -1-C）

本批在白天窗口自主推进（用户「执行吧」总授权 + 「继续」持续授权），无交互提问，决策点逐条披露：

| # | 决策 | 理由 |
|---|---|---|
